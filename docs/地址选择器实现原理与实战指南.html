地址选择器实现原理与实战指南

从数据来源 → 组件原理 → 前后端衔接 → 移动端适配，完整拆解「选择中国省市区」是怎么实现的

一、整体流程速览

一句话概括： 把一份「全国省市区 JSON 数据」放进项目本地，前端用 Element Plus 的级联选择器（el-cascader）按省→市→区逐级展开选择，选中后把名称写回表单提交给后端。

② 落地为本地 JSON
→
③ el-cascader 渲染级联
→
④ 选中值回显/回写
→
⑤ 提交后端保存

整套方案的核心卖点是： 前端零运行时依赖、后端零改动、数据静态化 。下面每一节拆开讲。

二、数据从哪来？—— 行政区划数据

中国行政区划是「省 → 市 → 区县」三级结构，官方数据由民政部维护。前端需要一份结构化数据，常见来源有 4 种：

来源 说明 本项目选择
npm 数据包 如 element-china-area-data 、 china-area-data ，把全国数据打包成 JS/JSON 选用（一次性提取）
后端接口 后端建表存省市区，前端调接口加载 未采用 （后端零改动原则）
第三方 API 如高德/腾讯地图行政区划 API 未采用 （需要 key、有调用限制）
手写硬编码 自己在代码里写死数据 不推荐 （几千条区县，维护灾难）

为什么用「一次性提取」而不是直接安装依赖？

当时的需求是： 不引入 vant/vanui 新 UI 库，不增加 npm 依赖 。做法是：

  1. 临时下载 element-china-area-data 数据包（仅用于提取， 不写入 package.json ）
  2. 用 Node 脚本把它的数据导出成纯 JSON： area.json （140KB）
  3. 放进项目 src/assets/data/ 目录，以后运行时完全不依赖那个 npm 包 
# 临时提取命令（在项目外临时目录执行，不入 package.json）
npm pack element-china-area-data@latest   # 下载压缩包
tar -xzf element-china-area-data-*.tgz     # 解压
node -e "const fs=require('fs');
const m=require('./package/dist/element-china-area-data.cjs');
fs.writeFileSync('area.json', JSON.stringify(m.regionData), 'utf8');"
设计启示： 「提取数据 → 静态化」是一种通用思路。像地区数据、词库、字典表这类 变动极低频 的数据，静态 JSON 远比每次发请求或引入大依赖划算。面试可以说「把低频变动数据静态化，减少运行时依赖与接口压力」。

三、数据长什么样？—— 树形结构

area.json 是 三层嵌套的树 ，每个节点长这样：

[ { "value": "110000", // 行政区划代码（省） "label": "北京市", // 显示名称 "children": [ // 下一级（市） { "value": "110100", "label": "北京市", "children": [ // 再下一级（区） { "value": "110101", "label": "东城区" }, { "value": "110102", "label": "西城区" } ] } ] }, { "value": "440000", "label": "广东省", "children": [ ... ] } ]
关键点： value/label/children 这个结构不是我们随便定的——它是 Element Plus 级联选择器 el-cascader 的 标准输入格式 。只要数据长这样，组件就能直接渲染。这也是「选数据源时先看组件要求」的体现。

value 是什么？

value 存的是 行政区划代码 （6 位数字，如 110000=北京市）。代码的作用：

  • 作为节点唯一标识，组件用它做选中/回显匹配（比用名称可靠，名称可能重名）
  • 提交给后端后可做校验（如判断是否真实存在的区划）

但本项目最终提交给后端的是 名称 （province/city/district 字符串），因为后端地址表存的是文本。所以需要做「代码 ↔ 名称」的转换，见第五节。

四、el-cascader 是怎么工作的？

el-cascader 是 Element Plus 的 级联选择器 。它的工作方式：

1. 渲染

把 options （就是 area.json）传进去后，组件内部递归渲染成多列面板： 

<el-cascader
  v-model="form.areaCodes"      // 选中结果（数组）
  :options="areaOptions"         // 数据源（树）
  placeholder="请选择省/市/区"
  clearable
/>
  • 初始只显示 第一列（省）
  • 点击某个省 → 右侧展开 第二列（该省下辖市）
  • 点击某个市 → 右侧展开 第三列（该市下辖区县）
  • 全部选完， v-model 得到 ['440000', '440100', '440106'] 这样的代码数组

2. v-model 的数据形态

form.areaCodes = ["440000", "440100", "440106"]
//                 ↑省      ↑市      ↑区（按层级顺序）

这个数组的长度 = 选择的层级数（本项目固定选到区，所以是 3）。它是「当前选中路径」的代码序列。

3. 面板是浮层（这导致了一个坑）

el-cascader 展开的面板是 teleport 到 body 的独立浮层 （popper）， 不 属于弹窗内部。所以：

  • 弹窗设 overflow: hidden 管不到它
  • 它的宽度由内容决定：每列默认 min-width: 180px ，三列就 540px
移动端坑： 375px 宽的手机屏幕，540px 的面板必然溢出，第三列被挤出屏幕。解法见第六节「移动端适配」。

五、核心流程：代码 ↔ 名称 的双向转换

这是整套逻辑里最需要讲清的部分。表单里有两个世界：

  • 组件世界 ：el-cascader 用「代码数组」工作（选中、回显）
  • 后端世界 ：地址表存「名称字符串」（province/city/district）

所以在「打开编辑弹窗」和「提交表单」两个时机，要做两次转换：

① 编辑回填：名称 → 代码（findAreaCodes）

后端返回 province/city/district 名称
→
遍历 areaOptions 树，按 label 逐级匹配
→
得到 [省代码, 市代码, 区代码]
→
赋给 form.areaCodes，级联自动回显
const findAreaCodes = (province, city, district) => {
  const codes = [];
  let level = areaOptions;                    // 从最顶层（省）开始找
  for (const name of [province, city, district]) {
    const node = level?.find(n => n.label === name);  // 在当前列按名称找
    if (!node) break;                          // 找不到就停（数据可能不匹配）
    codes.push(String(node.value));
    level = node.children;                     // 下钻到子级继续找
  }
  return codes;
};

② 提交写回：代码 → 名称（findAreaNames）

用户选中 form.areaCodes（代码数组）
→
按 value 逐级反查 label
→
写回 form.province/city/district
→
剥离 areaCodes 后提交后端
const findAreaNames = (codes) => {
  const names = [];
  let level = areaOptions;
  for (const code of codes) {
    const node = level?.find(n => String(n.value) === code);  // 按代码找
    if (!node) break;
    names.push(node.label ?? "");
    level = node.children;
  }
  return names;
};

// 提交前调用
if (form.areaCodes.length === 3) {
  const [province, city, district] = findAreaNames(form.areaCodes);
  form.province = province || form.province;
  form.city = city || form.city;
  form.district = district || form.district;
}
// 提交时剥离前端专用字段（避免多余字段发给后端）
const { areaCodes, ...payload } = form.value;
await AddressAPI.update(payload);

③ 校验规则

把「必须选完整三级」做成表单校验，未选够三级不允许提交：

areaCodes: [
  { required: true, type: "array", min: 3, message: "请选择省/市/区", trigger: "change" }
]
面试可讲点： 这是一个典型的「 前端展示模型 ≠ 后端持久化模型 」问题。组件要代码、后端要文本，于是用两个纯函数做双向映射。类似的还有：日期格式化、状态枚举的 code/文本互转。

六、移动端适配：解决面板溢出

问题回顾：级联面板是 body 浮层，每列默认 180px，三列 540px > 375px 视口 → 第三列消失。

解法：窄屏下面板宽度压到视口宽，列均分

在全局样式 src/styles/index.scss 加一条媒体查询： 

@media (max-width: 768px) {
  .el-cascader-panel {
    width: 100vw;          // 面板占满视口，不再被 540px 撑爆
    max-width: 100vw;
  }
  .el-cascader-menu,
  .el-cascader-menu__wrap {
    min-width: 0;          // 取消每列 180px 下限
    flex: 1 1 0;           // 三列均分视口宽度
  }
}

效果：省/市/区三列各占约 1/3 屏幕，完整显示。放在 全局样式 是因为面板在 body 层，组件内部的 scoped 样式（带 data-v 属性）作用不到它。

代价： 每列变窄后，「内蒙古自治区」这类长名称会被省略号截断。可接受（选中后能看到全名），也可再做「分步选择器」优化，属进阶项。

七、方案对比：为什么选这条路线

方案 优点 缺点 结论
el-cascader + 本地 JSON
本项目 		零依赖、零后端改动、加载快、代码量少 数据要自己维护更新 电商场景足够用
引入 vant 的 van-area 移动端交互成熟、有全国数据 双 UI 库并存、体积大、样式冲突风险 为一个组件引入整个库，不划算
三个 el-select 手动联动 无新依赖 要写省→市→区过滤逻辑，数据还得自带 重复造轮子
后端接口 / 地图 API 数据实时权威 后端要建表、接口要联调、第三方要 key 杀鸡用牛刀

决策逻辑（面试可以这样讲）

  1. 需求本质 ：省市区数据变动极低频（一年几次），不需要实时性 → 静态化
  2. 技术栈约束 ：项目已是 Element Plus 生态，不该为单组件引入第二个 UI 库 → 用 el-cascader
  3. 后端零改动 ：地址表字段不变（province/city/district 文本）→ 前端自转换即可
  4. 成本收益 ：140KB 静态数据 vs 后端建表+接口+缓存，前端方案显著更省

八、动手实践：5 步自己复现

  1. 拿数据 ：下载一份省市区 JSON（或直接复制本项目的 src/assets/data/area.json ）
  2. 放数据 ：放进 src/assets/data/ ，在组件里 import areaData from "@/assets/data/area.json" （需 tsconfig 开启 resolveJsonModule ）
  3. 接组件 ：写一个 el-cascader，绑定 options 和 v-model
  4. 写转换函数 ：复刻 findAreaCodes / findAreaNames 两个函数（上面有完整代码）
  5. 测流程 ：新增（选三级→提交→看后端收到名称）、编辑（后端返回名称→弹窗自动回显）

完成这 5 步，你就完整走通了一遍「静态数据 + 级联组件 + 双向转换」的地址选择实现。
