# 秒杀商品功能设计文档

> 版本：v1.2 · 2026-08-07 · 状态：✅ 已实现并通过端到端联调（四项关键决策均已确认采用，实现后已完成全链路验证）
> 背景：现有"限时秒杀"仅支持**秒杀优惠券**（场次关联 coupon，抢到的是券）。本方案在不破坏现有秒券功能的前提下，新增**秒杀商品**能力（限时低价抢购某商品，抢到生成待支付订单）。

---

## 1. 目标与范围

### 1.1 目标

- 管理员可发布"秒杀商品"场次：绑定商品（可选 SKU）+ 秒杀价 + 秒杀库存 + 限购数量 + 活动时间
- 用户在前台秒杀页一键抢购 → 生成**待支付秒杀订单**（秒杀价）→ 去支付
- 与现有"秒杀优惠券"**共存**，同一套场次管理页/状态机/限流框架

### 1.2 非目标（本期不做）

- SKU 级差异化秒杀价（一个场次一个秒杀价，MV）
- 秒杀商品叠加优惠券
- 秒杀定金/尾款模式
- 商家端独立发布秒杀（仅管理员发布）

## 3. 关键决策（已确认）

> 四项决策均已按推荐方案确认：**复用场次表扩展 · 直接生成待支付订单 · 场次级价格 · 双库存扣减**

### 决策 1：数据模型 —— 复用 `seckill_session` 表扩展（✅ 已确认）

| 方案 | 说明 | 评估 |
|------|------|------|
| **A. 复用场次表扩展**（推荐） | 表加 `seckill_type`、`product_id`、`sku_id`、`seckill_price` 四列，`coupon_id` 允许为空 | 管理页/状态机/Redis 库存/限流/定时任务全部复用，改动最小；两种模式字段互斥 |
| B. 新建 `seckill_product` 表 | 独立表存商品秒杀场次 | 表结构更"干净"，但状态机/Redis 键/页面/定时任务需双写双查，工作量翻倍 |

**默认采用方案 A**（✅ 已确认）。秒杀商品与秒杀券共用 `seckill_session`，通过 `seckill_type` 区分：
- `seckill_type = 0`：秒券（`coupon_id` 必填，现有逻辑不变）
- `seckill_type = 1`：秒商品（`product_id`、`seckill_price` 必填）

### 决策 2：秒杀价粒度 —— 场次级价格（✅ 已确认）

- 一个场次一个秒杀价 `seckill_price`，可指定 `sku_id`（有 SKU 商品）或留空（无 SKU 商品）
- SKU 级不同秒杀价：本期不做，后续可加 `seckill_sku` 表

### 决策 3：抢购产物 —— 直接生成待支付秒杀订单（✅ 已确认）

| 方案 | 说明 |
|------|------|
| **A. 抢到即锁单**（推荐） | 抢购请求携带 `addressId`（用户默认地址），成功后**直接创建待支付订单**（秒杀价），前端跳订单详情/支付页 |
| B. 抢到资格再结算 | 抢购成功生成资格，跳转结算页选地址再下单 | 多一步交互，但可临时换地址；需新增资格表 |

**默认采用方案 A**（✅ 已确认）：抢购请求带 `addressId`；若用户无收货地址，前端提示先完善地址。超时未支付（30 分钟）由现有任务自动取消并回滚全部库存。

### 决策 4：库存扣减 —— 双库存扣减（✅ 已确认）

- 秒杀库存（`seckill_stock` + Redis）负责"限时放量"闸门
- 商品/SKU 实际库存同步扣减，防与普通销售渠道超卖叠加（订单取消时由现有逻辑回滚）
- 创建场次时校验：`seckill_stock <= product/sku 当前库存`

## 4. 数据模型变更

```sql
-- seckill_session 表新增字段（MySQL）
ALTER TABLE `seckill_session`
  ADD COLUMN `seckill_type`    TINYINT      NOT NULL DEFAULT 0 COMMENT '0=秒杀优惠券 1=秒杀商品',
  ADD COLUMN `product_id`      BIGINT       NULL COMMENT '秒杀商品ID（type=1）',
  ADD COLUMN `sku_id`          BIGINT       NULL COMMENT '指定SKU ID（type=1，可选）',
  ADD COLUMN `seckill_price`   DECIMAL(10,2) NULL COMMENT '秒杀价（type=1）';
```

说明：
- `coupon_id` 改为可空（type=1 时不填）
- 逻辑约束：`(type=0 AND coupon_id NOT NULL) OR (type=1 AND product_id NOT NULL AND seckill_price NOT NULL)`

## 5. 后端改造（E:\idea_workspase\e-shop）

### 5.1 实体 & DTO

- `SeckillSession.java`：新增 `seckillType/productId/skuId/seckillPrice`；新增非库字段 `productName/coverImage/originalPrice`（列表展示，`@TableField(exist=false)`）
- `SeckillSessionSaveDTO.java`：新增 `seckillType/productId/skuId/seckillPrice`，`couponId` 校验改条件
- `SeckillSessionVO.java`：新增上述字段，商品模式带商品图/原价/名称

### 5.2 Service（SeckillServiceImpl）

- `create()`：按 type 分流校验
  - type=1：校验商品存在、上架、`seckillPrice > 0`、`seckillStock <= 商品(或SKU)库存`、秒杀价 < 商品原价（可选）
- `update()`：type=1 修改商品时重复上述校验
- `seckill()` 新增商品分支（type=1）：
  1. 复用现有：场次/时间/状态校验 → 防重复抢购（Redis Set）→ Redis 扣库存 → SADD
  2. **原子扣减商品/SKU 库存**（同一事务，防超卖；SKU 场景同步回写 product.stock）
  3. 调用**秒杀下单**：单商品、数量=1、`pay_amount = seckill_price`、`order_status = 0`（待付款）、`pay_status = 0`、`order.type` 标记秒杀（新增字段或复用，见 5.4）、收货信息取 `addressId`
  4. 任一步失败：回滚 Redis（increment + SREM）与 DB 扣减，抛出异常
- **超时回滚**：秒杀订单被自动取消时（现有 30 分钟任务），额外将 `seckill:stock:{sessionId}`、`seckill_session.seckill_stock` 加回，并从 `seckill:users:{sessionId}` 移除该用户
- `delete()/cancel()/preheatStock()`：逻辑不变（已按场次维度清理 Redis）

### 5.3 Controller

- `SeckillController.seckill()`：`@RequestBody` 改收 `{ addressId }`（可空则提示完善地址），内部按 type 分流

### 5.4 订单标识（推荐最小改动）

- `order` 表新增 `seckill_session_id BIGINT NULL`（秒杀来源标记），`order.type` 语义不动
- 好处：秒杀订单取消/退款时能定位场次做库存回滚

## 7. 并发与数据一致性

| 环节 | 机制 |
|------|------|
| 防超卖（秒杀库存） | Redis `DECR` 原子扣 + `seckill_session.deductStock` 行级原子扣（现有） |
| 防超卖（商品库存） | 同事务 `UPDATE product_stock/sku_stock = stock - 1 WHERE stock >= 1` |
| 防重复抢购 | Redis `SADD` + 幂等（现有） |
| 兜底回滚 | 落库异常 → Redis 回补 + DB 回补（现有模式扩展） |
| 未支付释放 | 复用 30 分钟自动取消任务，秒杀订单额外回滚秒杀库存 |
| 撤销/删除场次 | 已产生的秒杀订单不受影响（订单独立成单） |

---

## 8. 安全与边界

- type=1 场次强制校验商品上架状态；场次开始时若商品已下架 → 自动撤销（仿照券失效逻辑）
- 秒杀价不得高于原价、不得为负；`seckill_stock` 不得超过商品实际库存
- 用户仅能通过秒杀接口创建秒杀订单（下单接口不暴露秒杀价）
- 已支付秒杀订单走现有退款流程（不影响秒杀库存回滚由退款单处理）

## 9. 测试计划

1. **管理端发布**：分别发布秒券 / 秒商品场次，校验必填项互斥、价格/库存校验
2. **抢购主链路**：商品模式抢购成功 → 生成待支付订单（秒杀价、数量 1）→ 支付成功状态流转
3. **防超卖**：并发 100 请求抢 50 库存，最终成功 50 单，Redis/DB/商品库存三者一致
4. **防重复**：同一用户二次抢购被拒
5. **超时释放**：秒杀订单 30 分钟未支付自动取消，秒杀库存与商品库存回滚、可被再次抢购
6. **异常回滚**：商品库存不足时抢购失败，Redis 库存与 users 集合回滚
7. **回归**：秒券模式功能不受影响（发券/限流/状态机）
