访问日志与日志管理实战指南

围绕你的 E-Shop 项目讲透三件事：访问日志该记什么、生产环境怎么管日志、日志报警怎么设计。先讲清"本项目怎么做"，再对照"真实生产怎么做"，最后给零经验学生一条可执行的学习路径。

1 板块一 · E-Shop 访问日志分类清单：应记录 vs 不应记录 先搞清楚"谁在污染数据"，再谈统计

1.1 本项目现有日志基础设施（先对齐事实）

你项目里访问日志的完整链路是这样跑的，面试被问到先把这条链路说清楚：

# 访问日志链路（E-Shop 现状） TraceFilter（com/shopsphere/eshop/config/TraceFilter） 请求入口生成 traceId → 放入 MDC → 异步发 RabbitMQ → VisitLogConsumer 消费落库 MySQL visit_log 表 → 监控大盘 MonitorMapper 查询（PV / UV / 趋势 / 热点路径 / 慢接口）

visit_log 表的列： id / user_id / ip / user_agent / request_uri / method / status_code / duration_ms / visit_time 。有了状态码和耗时字段，才能算错误率和慢接口——这是 2026-09-14 那次扩展加上的。

💡
为什么是"异步"？ 日志是低优先级数据，绝不能因为写日志把用户的下单请求拖慢。你用的有界线程池/队列 + 丢弃策略就是这个道理：日志允许丢一点，业务不能卡一秒。

1.2 已经在排除的请求（写死的事实，别动）

判断函数 排除对象 理由
isStaticResource 静态资源（css/js/图片）、/actuator/、swagger/v3/api-docs 静态资源不代表真实业务行为；actuator 是运维探活、api-docs 是文档生成，都会周期性被访问，记了纯属噪音。
isNoiseEndpoint /api/v1/notices/unread-*（unread-count、unread-list）、/api/merchant/messages/unread-count 这是"小红点"轮询接口，前端每 30 秒拉一次。如果计入，PV 会被轮询刷爆，趋势图全是假的。

1.3 建议分类一：应该记录（代表真实用户行为）

类别 / 接口路径 前端调用方式 记录理由（面试讲这些）
商品类 /api/product/*（详情、搜索、热卖） 用户点商品、搜关键词、看热卖榜 PV 主力来源；搜索词是运营热词的数据基础，详情页访问量直接反映商品热度。
交易类 /api/order/*（下单、列表、详情） 下单、查订单 转化漏斗关键一环，从"浏览→下单"的每一步都在这张表里可追溯。
支付 /api/pay/alipay/*（尤其异步通知 notify 回调） 后端回调 + 前端支付结果轮询 支付宝 notify 回调必须留痕 ：审计、对账、排查"支付成功但订单没更新"全靠它。这条是重点中的重点。
退款 /api/refund/* 用户申请退款、商家审核 资金敏感操作，留痕用于审计与纠纷取证。
秒杀抢购 /api/seckill/* 秒杀页抢购按钮 高并发路径，监控并发量、失败率、超卖风险；压测数据（QPS 217.9→365.9）就是靠它验证的。
加购 /api/cart/*、领券 /api/user/coupons/* 加购物车、领优惠券 购物车是转化漏斗第二环；领券是营销活动效果的量化指标。
收藏 /api/favorite/*、评论 /api/comments/*、浏览历史 /api/product/history/* 收藏、评论、浏览记录 用户兴趣画像的来源，运营做推荐、做内容都靠这些行为数据。
登录注册 /api/user、/api/auth/email 登录、邮箱验证码登录 账号安全审计：异常登录、暴力破解的检测都从登录日志开始。
管理端 /admin/*、/api/admin/* 管理后台操作 管理员操作审计，出问题能定位"谁在什么时候改了什么"。
活动签到 /api/user/activities、/api/group-buy、/api/marketing-activity 签到、拼团、营销活动 活动参与度统计，判断活动 ROI 的核心数据。
商家端 /merchant/* 商家后台 商家操作审计 + 商家活跃度（你的 B2B2C 多租户模式下尤其重要）。

1.4 已新增排除（噪音，已落实到 TraceFilter.isNoiseEndpoint，2026-09-26）

接口路径 为什么是噪音 排除做法
/api/captcha 验证码图片生成 带随机参数，用户每刷新一次页面就调一次，容易刷屏、污染 PV。 图片生成请求不记录； 校验动作可以留 （校验是真实行为）。
/api/v1/sse/connect（SSE 长连接建立） 长连接建立一次就挂着，不代表页面访问次数；断线重连还会反复建立。 已排除。SSE 的活跃度用连接数/心跳统计，不走 visit_log。
/api/admin/monitor/*（监控页 loadAll 轮询） 监控页前端自动刷新、定时 loadAll，自己污染自己的访问日志，监控数据越统计越假。 已排除，不然"监控大盘"统计出的热点路径会被自己顶上去。
秒杀场次状态查询 /api/seckill/sessions（每 10 秒轮询） 轮询频率高，纯状态查询，代表不了真实抢购行为。 已排除；抢购动作（/api/seckill/* 下单）仍然保留。

1.5 边界情况：想清楚再决定

接口路径 情况 结论
/api/pay/alipay 支付结果页轮询（查询） 用户主动打开结果页时的 短时轮询 ，不是后台自动刷。 建议保留 ——它和你的对账自愈 reconcilePendingTransactions 呼应：轮询查询 + 定时对账，是支付闭环的一部分，留痕有助于排查对账不一致。
首页 / 分类页 / 活动聚合页 低频（相对轮询），用户真正打开的行为。 保留 ——首页 PV 是运营最看重的指标之一。
⚠️
核心原则一句话： 记录"用户的真实意图行为"，排除"机器自动触发的周期行为"。面试官问你为什么这么分类，就答这一句，然后举你项目里的例子（轮询、SSE、captcha）。

2 板块二 · 真实项目中访问日志一般统计哪些接口与指标 从"我有一张表"到"我知道发生了什么"

2.1 通用指标清单（面试必背）

指标 定义 典型用途
PV / UV 页面浏览量 / 独立访客数（按 user_id 或 cookie 去重） 整体流量水位，运营日报的核心数字。
独立 IP 按 IP 去重 粗粒度覆盖度；也能侧面发现单 IP 爬虫。
热门 URI TopN 请求量最高的 N 个路径 发现热点功能、判断功能入口设计是否合理。
状态码分布 2xx/3xx/4xx/5xx 占比 接口健康度的第一眼；5xx 占比高立刻报警。
5xx 错误率 5xx 请求 / 总请求 服务可用性的核心红线指标。
平均耗时 / P99 平均响应时间 / 99 分位耗时 P99 代表"最差的那 1% 用户的体验"，比平均值更能暴露问题。
峰值 QPS 每秒请求数最大值 容量规划依据：要不要加机器、限流阈值设多少。
时段分布 按小时/天的流量曲线 发现高峰时段，安排限流和扩容节奏。
转化漏斗 曝光→详情→加购→下单→支付 定位用户在哪一步流失最多，是电商最值钱的指标。

2.2 采集层：生产环境一般怎么收日志

方案 组成 适用场景
Nginx access log + ELK Filebeat（采集）→ Logstash（清洗）→ Elasticsearch（存储检索）→ Kibana（可视化） 业界最经典组合；Nginx 网关层记访问日志，业务层记应用日志。
Loki + Promtail + Grafana Promtail 采集 → Loki 存日志 → Grafana 展示 云原生 / K8s 场景，轻量，和 Prometheus 指标体系同框展示。
云厂商 SLS 阿里云日志服务（采集 + 检索 + 告警一体） 国内上云团队最省事的选型，免运维。
业务访问日志落库（本项目方式） TraceFilter → RabbitMQ → MySQL visit_log → 监控大盘 适合做业务维度统计（漏斗、热词、用户行为），和生产方案不冲突、互补。
💡
访问日志 ≠ 应用日志，这个区别必须讲清： 访问日志回答"谁访问了什么、快不快、成没成功"（数据驱动运营与容量规划）；应用日志回答"为什么失败"（异常栈、业务上下文）。你的项目里 visit_log 是访问日志，logback 输出的 eshop.log 是应用日志，两条线。

2.3 统计口径实践：真实项目通常不纳入统计的请求

请求类型 识别方式 处理
健康检查 /actuator/health、K8s liveness/readiness probe 排除，或单独统计为"探活成功率"。
静态资源 后缀 .js/.css/.png/.jpg，或 CDN 已拦截 排除；静态资源由 CDN 统计。
轮询 短间隔重复请求同一 URI（unread-count、订单状态） 排除，防止 PV 虚高。
爬虫 / 扫描器 User-Agent 特征 + IP 频控 + 访问模式 标记或排除；你的项目日志里常见的 Infrawatch、zgrab 就是扫描器，被 WAF 拦截返回 403 的记录。
监控自查询 监控系统 / 大盘自身拉数据的接口 排除，避免自己污染自己的统计。
压测流量标记 请求头 X-Load-Test: 1 或专属 UA 打标后单独统计，或直接排除，避免混进线上指标。
⚠️
用 UA 识别爬虫/扫描器的实操： 扫描器 UA 通常带明显特征（Infrawatch、zgrab、masscan、python-requests 不带浏览器头等），做法是：查 visit_log 里 UA 含这些关键字的记录 → 看 IP 是否高频 403 → 进 IP 黑名单或加频控。你的项目已经在做 WAF 层拦截，日志里留着的 403 记录正好用来验证拦截是否生效。

3 板块三 · 日志应该如何管理 分类、级别、格式、链路、存储、检索

3.1 日志分类（一张表背下来）

分类 内容 典型产出
应用日志 业务日志（下单、退款、秒杀）+ 框架日志（Spring、MyBatis） eshop.log / eshop-error.log（logback 输出）
访问日志 请求级记录：谁、什么路径、多快、成没成功 visit_log 表（本项目）+ Nginx access log（生产）
慢查询日志 MySQL 中执行超过阈值的 SQL MySQL slow_query_log；配合 EXPLAIN 分析
系统日志 OS / 中间件 / 容器日志（Linux syslog、Docker、JVM GC） dmesg、GC log、容器 stdout
审计日志 管理员操作、资金变动、越权尝试 操作日志表（防误操作）、敏感操作留痕

3.2 级别规范：ERROR / WARN / INFO / DEBUG / TRACE 怎么取舍

级别 什么时候用 反例（你的项目踩过的坑）
ERROR 系统级故障：异常未捕获、DB 连接失败、MQ 消费失败、OOM 前兆 把"业务可预期的拒绝"打成 ERROR 会刷屏告警。
WARN 异常但可降级：重试后成功、参数不合法、缓存穿透走了 DB 用 INFO 打大量参数错误，浪费存储。
INFO 关键流程节点：下单成功、支付回调收到、对账完成 把每个方法进出的都打 INFO，一天几个 G。
DEBUG 开发期排查、高并发路径的细节打点（生产默认关） 秒杀拒绝路径（重复/售罄）就该用 debug ，而不是 info/warn。
TRACE 极细粒度链路追踪，基本只在定位疑难 bug 时临时开 生产常开 TRACE = 磁盘爆炸。
⛔
本项目真实教训（面试能打的一手牌）： 秒杀拒绝路径（重复抢购、售罄）当初用了 info/warn 级别。同步 ConsoleAppender 在高并发写日志时因为 写锁串行化 形成洪峰，日志反而成了瓶颈。改成 debug 级别后（同步输出、高并发下不再抢锁刷屏），压测实测： QPS 从 217.9 提到 365.9，P99 从 2425ms 降到 174ms 。结论：高并发路径的日志级别也是性能参数，不是随便定的。

3.3 格式规范

统一格式是"能查"的前提。你的 logback-spring.xml 已经带了 traceId、线程、类名、时间戳，这个习惯保持下去。推荐格式要素：

2026-09-26 14:32:01.123 [a1b2c3d4e5f6a7b8] INFO [http-nio-8080-exec-7] c.s.e.service.impl.OrderServiceImpl : 订单创建成功 orderNo=20260926143201001

① 时间戳 ：精确到毫秒，统一时区（Asia/Shanghai）； ② traceId ：贯穿一次请求； ③ 级别 ； ④ 线程名 ：定位并发问题； ⑤ 类名 ：快速跳代码； ⑥ 消息 ：业务上下文（订单号、用户 ID 这种"可检索的关键字"一定要带）。

生产推荐结构化 JSON 日志 （用 logstash-logback-encoder），字段化之后 ES/Loki 才能按字段检索、聚合，而不是对着文本正则抠：

# 结构化 JSON 日志（生产环境推荐，示意） {"@timestamp":"2026-09-26T14:32:01.123+08:00", "level":"INFO","traceId":"a1b2c3d4e5f6a7b8", "thread":"http-nio-8080-exec-7", "logger":"c.s.e.service.impl.OrderServiceImpl", "message":"订单创建成功","orderNo":"20260926143201001"}

敏感字段脱敏 ：密码、手机号、token 一律不落日志。打印对象前先想一句"这行日志会不会进审计报告"——手机号中间四位打星，token 只打前几位。

3.4 链路追踪

你的 TraceFilter 在请求入口生成 traceId 并放进 MDC，logback 的 pattern 里打了 [%X{traceId}]，所以一次请求的所有日志都带同一个 traceId。生产里这就是跨服务排查的锚点：

# 排查套路：先拿 traceId，再按它串日志 grep "a1b2c3d4e5f6a7b8" eshop.log # 把这次请求的日志全捞出来 grep "a1b2c3d4e5f6a7b8" eshop-error.log # 看这次请求有没有报错
💡
进阶（生产/微服务）： traceId 通过 HTTP 头（你项目里是 X-Trace-Id）跨服务传递，配合 spanId/parentId 就变成完整的分布式追踪（SkyWalking、Zipkin 都在做这件事）。你项目的做法已经是它的雏形。

3.5 存储与轮转

日志不能无限长，必须有滚动策略： 按大小滚动 （单个文件到 100MB 切一个）、 按时间滚动 （每天/每小时一个文件）、 保留期 （30 天）、 归档压缩 （.gz 冷存）、 磁盘容量规划 （估算：QPS × 每行日志字节数 × 时长 = 容量）。

你项目 logback-spring.xml 里 prod 环境已经配了滚动 （RollingFileAppender：按天 + 100MB 触发，保留 30 天，ERROR 单独一个文件），这套配置本身就可以当面试素材讲。假如某个环境没配，补齐做法如下（参考你现有配置）：

# logback-spring.xml 补滚动策略（示意，prod profile 内） <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender"> <file>./logs/eshop.log</file> <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy"> <fileNamePattern>./logs/eshop.%d{yyyy-MM-dd}.%i.log</fileNamePattern> <maxHistory>30</maxHistory> <timeBasedFileNamingAndTriggeringPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedFNATP"> <maxFileSize>100MB</maxFileSize> </timeBasedFileNamingAndTriggeringPolicy> </rollingPolicy> </appender>

3.6 采集与检索：方案怎么选

方案 核心组件 适用规模
ELK / EFK ES + Logstash/Fluentd + Kibana（+ Filebeat） 中大型、检索和聚合要求高；成本高、运维重。
Loki Promtail + Loki + Grafana 云原生、只想"能搜"不想建索引；成本低。
阿里云 SLS 采集 + 检索 + 告警一体 上云团队；免运维，按量付费。
直查 MySQL（本项目） visit_log 表 + MonitorMapper 小项目完全够用 ：单机日 PV 几万级别，索引建好后秒级返回；等量级上来再上 ES 不迟。
⚠️
规模边界要诚实： visit_log 直查 MySQL 的瓶颈在于：① 表行数大了聚合变慢（需要分区/归档）；② 全文检索能力弱（搜不到消息体里的关键字）；③ 日志增长吃掉业务库磁盘。当你发现 MonitorMapper 的聚合查询开始超 1 秒、或表超过千万行，就该考虑把访问日志挪到独立存储（ClickHouse/ES/SLS）。

4 板块四 · 日志报警怎么设计与处理 让日志从"事后翻"变成"事前喊"

4.1 告警规则设计（阈值 + 持续时长，缺一不可）

规则 示例阈值 + 持续时长 为什么这么设
5xx 率突增 近 5 分钟 5xx 率 > 5% 且持续 2 分钟 只看瞬时容易误报（一次压测抖动就触发）；持续才代表真故障。
P99 超阈值 P99 > 1000ms 且持续 5 分钟 慢是慢性病，给它一点观察窗口，避免偶发抖动误报。
ERROR 关键字 ERROR 日志中匹配 OOM、Connection refused 等关键字 关键字告警必须"精准"，否则 ERROR 一多就疲劳。
磁盘/内存水位 磁盘使用率 > 85%、堆内存 > 80% 持续 10 分钟 水位告警要提前量，等 100% 就晚了。
支付对账失败 对账发现不一致订单数 > 0（立即告警） 钱的事优先级最高，一条不一致就要人工介入。
秒杀超卖检查 库存扣减后 stock < 0（立即告警，P0） 超卖是资损，发现即处理。

4.2 告警分级：P0 → P3

级别 含义 例子
P0 立即处理，可能资损或全站不可用 支付故障、全站 5xx 飙升、DB 挂了、超卖。
P1 高优处理，影响核心功能但可临时降级 下单接口 P99 大幅上升、MQ 消费积压。
P2 计划内处理 磁盘水位告警、非核心接口偶发 5xx。
P3 记录观察，不打扰值班 爬虫频次上升、某页 PV 异常波动。

4.3 降噪：别让告警变成"狼来了"

  • 聚合 ：同一 traceId / 同一接口的 N 条 ERROR 合并成 1 条告警，附数量。
  • 去重 ：同一个问题 5 分钟内不重复发（第一次发，之后进入静默）。
  • 静默窗口 ：已知维护窗口（发版、压测）提前静默，避免误报。
  • 值班时间窗 ：P3 只在工作时间提醒，P0 24 小时响。
  • 目标 ：告警要少而准，宁可漏掉 3 条不重要的，也不要 1 天 50 条把值班人搞麻。

4.4 值班处理流程（背下来，面试直接演）

# 收到告警后的标准动作（按顺序） ① 确认影响面 ：这条告警影响谁？多大范围？先看一眼大盘 ② 看监控 ：QPS / 错误率 / 资源水位，判断是入口流量还是服务本身 ③ 看日志定位 ：grep traceId / 关键字，找到具体报错和调用链 ④ 止血 ：先恢复可用（降级 / 限流 / 回滚），再谈根治 ⑤ 修复 ：改代码 / 加索引 / 扩资源 ⑥ 验证 ：观察指标回落、错误消失 ⑦ 复盘 ：写事故报告：时间线 / 根因 / 影响 / 改进项

4.5 项目落地建议：给你的 E-Shop 设计一个"轻量告警"

个人项目没条件上 Prometheus，但你完全可以用 @Scheduled 定时任务 做一个轻量告警：每 2 分钟扫一次 visit_log 近 5 分钟的 5xx 率，超阈值就调企业微信/钉钉 webhook（或发邮件），这样睡觉时手机也会响——这也是面试亮点："我自己给项目做了告警闭环"。

# 轻量告警核心思路（示意，非完整代码） @Scheduled(fixedDelay = 120_000) // 每 2 分钟跑一次 public void check5xxRate() { // 1. 查 visit_log 近 5 分钟数据 // SELECT COUNT(*), SUM(status_code >= 500) // FROM visit_log WHERE visit_time > NOW() - INTERVAL 5 MINUTE // 2. 若 5xx 率 > 5% 且连续两次触发 → 调企业微信/钉钉 webhook // POST { "msgtype":"text", "text":{ "content":"5xx率异常: 12%" } } // 3. 触发后 5 分钟静默（Redis 存 lastAlarmTime），防刷屏 }
💡
和现有代码联动： 你已经有 reconcilePendingTransactions（每 5 分钟对账兜底）在跑，把它升级成"对账发现不一致 → 立即告警 + 标记退款"，支付侧的可观测闭环就完整了：支付宝回调 → 结果页轮询 → 定时对账 → 异常告警。

5 板块五 · 零经验学生如何学习看日志、管日志、处理日志报警 四个阶段，从"会读"到"懂体系"

阶段 1：会读（从自己项目开始）

  • 启动 E-Shop 后端，观察控制台：INFO 是正常流程、ERROR 是异常，先分清"哪些是框架噪音、哪些是业务日志"。
  • 故意制造一个异常 ：调一个不存在的接口（404）、把某张表临时删掉再请求（SQL 报错），逐行解读异常栈：Exception 类型 → 出错方法 → 哪一行 → 根因。
  • 看到日志先回答三个问题：发生了什么？在哪个类哪一行？需要我处理吗？

阶段 2：会查（把日志当工具用）

  • grep / 关键字 / 时间窗口 ：报错发生在 14:30 到 14:32 之间，就 grep 这个窗口的 ERROR；再拿 traceId 串联一次完整请求（前面 3.4 的套路）。
  • EXPLAIN 定位慢 SQL ：慢接口 → 看 MyBatis 打的 SQL → EXPLAIN 看 type/索引 → 加索引或改写法。你的文档里已经有这个实操。
  • jstack 抓线程栈 ： jstack <pid> > dump.txt ，看线程在等什么锁、卡在哪个方法。 本项目实战： 压测中发现单请求 46ms，抓 jstack 定位到 jjwt 每次解析都触发 ServiceLoader 全 classpath 扫描（打开 100+ JAR），把 JwtParser 改成全局复用单例后，单请求 46ms → 23ms 。这是"拿证据定位性能"的标准打法。

阶段 3：会管（自己搭闭环）

  • 自己给项目配 logback 滚动（按天 + 大小 + 保留期），重启观察文件切分。
  • 写告警脚本（4.5 的 @Scheduled 思路落地成代码）。
  • 做故障演练 ：人为让一个接口返回 500（临时抛异常），观察告警是否触发、visit_log 里的 5xx 率是否抬头、日志能否按 traceId 定位到根因——演练完记得还原。

阶段 4：懂体系（概念扫盲 + 拓宽视野）

  • 概念扫盲 ：ELK/EFK、Loki、Prometheus + Grafana、阿里云 SLS——知道各自解决什么问题、大概的组件组成（板块三 3.6 的表格先背熟）。
  • 看官方文档 + 可视化操作 ：有条件就用 Docker 起一个 ELK 或 Grafana + Loki 玩一周；没条件就看官方文档截图，能说出 Kibana 怎么按字段过滤、Grafana 怎么加面板。
  • 了解 on-call 值班文化 ：生产事故分级、值班交接、事故复盘（postmortem）——面试聊到"团队协作"时这是加分话题。
