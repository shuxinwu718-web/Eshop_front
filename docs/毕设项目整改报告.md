## 1. 整改概述

本系统为前后端分离电商平台：后端 **Spring Boot 3.2 + Spring Security + MyBatis-Plus + MySQL + Redis + Elasticsearch**，前端 **Vue 3 + TypeScript + Vite + Element-Plus**。

整改工作基于**全量代码审查、安全扫描与并发推演**发现的 19 项问题（其中高危 13 项），按照「安全 > 数据一致性 > 前端可用性」的优先级完成修复。整改完成后通过**单元测试 + 接口实测 + 构建验证**三层手段确认系统功能正常、风险已消除。

**整改原则**：
- 最小改动：针对根因修改，不重构无关代码；
- 原子校验：并发场景统一采用「条件 UPDATE + 受影响行数判断」，不引入分布式锁等复杂方案；
- 验证闭环：每项修复均通过编译、测试或接口实测确认。

## 3. 安全类问题整改

### 3.1 S1 方法级安全未启用，`@PreAuthorize` 全部失效

**问题描述**：启动类缺少 `@EnableMethodSecurity`（Spring Security 6 起不再默认开启），导致全部 18 处方法级权限注解不生效，任何已登录用户均可调用本应受限的接口。

**修复方案**：

```java
@EnableScheduling
@EnableMethodSecurity   // 新增
@SpringBootApplication
public class EShopApplication { ... }
```

**验证结果**：`EShopApplication.java` 已确认添加注解；接口实测普通用户访问管理接口返回 **HTTP 403**。

### 3.2 S2 管理端接口无角色控制

**问题描述**：`AdminSeckillController`、`AdminCouponController`、`AdminRefundController`、`AdminMerchantApplyController` 等无任何权限注解，任意注册用户可直接创建秒杀、发券、审核退款。

**修复方案**：在开启方法级安全基础上，为各管理 Controller 补齐类级/方法级 `@PreAuthorize("hasRole('ADMIN')")`；退款审核按业务拆分为商户/管理员双角色。

**验证结果**：全部管理 Controller 已带权限注解；实测普通用户访问 `/api/admin/dashboard/stats` 返回 **HTTP 403**。

### 3.3 S3 优惠券越权使用（IDOR）

**问题描述**：下单时传入他人 `userCouponId` 可盗用其优惠券抵扣，属于不安全的直接对象引用。

**修复方案**：

```java
if (userCoupon != null && !userCoupon.getUserId().equals(userId)) {
    throw new BusinessException("优惠券不属于当前用户");
}
```

**验证结果**：`OrderServiceImpl.java:138` 已确认归属校验，跨用户券下单被拒绝。

### 3.4 S4 匿名文件上传 + 无类型白名单

**问题描述**：`/api/v1/files/**` 匿名放行且无扩展名白名单，可上传恶意 HTML/JS 造成存储型 XSS。

**修复方案**：
1. 接口改为 `authenticated()`；
2. `FileUploadController` 增加扩展名白名单（jpg/png/gif/webp 等）；
3. 静态资源 `/uploads/**` 显式放行保证图片可访问。

**验证结果**：未登录上传返回 401；非白名单扩展名被拒绝。

### 3.5 S5 敏感信息硬编码

**问题描述**：SMTP 授权码、JWT 密钥、MySQL 密码硬编码于配置文件。

**修复方案**：改为环境变量注入（`${MAIL_PASSWORD:xxx}`、`${JWT_SECRET:xxx}`），保留开发默认值便于本地运行。

**验证结果**：配置支持 `${ENV}` 注入；生产部署可覆盖默认值。

### 3.6 S6 密码重置验证码删除键错误

**问题描述**：写入 Redis 的键为 `email:code:{email}:reset`，删除时却使用 `email:code:{email}`，验证码永不被删除，可无限复用重置任意账号密码。

**修复方案**：删除键与写入键保持一致：

```java
redisTemplate.delete("email:code:" + request.getEmail() + ":reset");
```

**验证结果**：`UserController.java:266` 已确认按写入键格式修复。

### 3.7 S7 登录安全缺陷：日志泄露完整 JWT + 图形验证码可绕过

**问题描述**：
1. `UserServiceImpl.login` 中 `log.info("生成的完整 token: {}", token)` 将完整 JWT 写入日志，一旦日志泄露，攻击者可凭 token 冒充用户（账号会话劫持）。
2. 图形验证码仅在同时传入 `captchaKey` 与 `captchaCode` 时才校验，攻击者直接不传验证码即可绕过图形验证码，配合撞库/暴力破解登入他人账号。

**修复方案**：
1. 移除完整 token 打印，仅记录用户名与会话版本号：
```java
// 整改前
log.info("生成的完整 token: {}", token);
// 整改后
log.info("用户 {} 登录成功，会话版本: {}", user.getUsername(), sver);
```
2. 验证码改为必填强校验，校验通过后立即删除（一次性防重放）：
```java
// 验证图形验证码（A1 整改：必填强校验，防止不传验证码绕过）
if (!StringUtils.hasText(request.getCaptchaKey()) || !StringUtils.hasText(request.getCaptchaCode())) {
    throw new BusinessException("验证码不能为空");
}
String cacheKey = "captcha:" + request.getCaptchaKey();
String cachedCode = redisTemplate.opsForValue().get(cacheKey);
if (cachedCode == null) {
    throw new BusinessException("验证码已过期，请刷新");
}
if (!cachedCode.equalsIgnoreCase(request.getCaptchaCode())) {
    throw new BusinessException("验证码错误");
}
// 验证通过后删除，防止重复使用
redisTemplate.delete(cacheKey);
```
3. `LoginRequest` 的 `captchaKey` / `captchaCode` 增加 `@NotBlank` 注解兜底（`UserController.login` 已启用 `@Valid`）。

**验证结果**（`lisi/123456` 真实环境实测）：

| 场景 | HTTP | 响应 |
|------|------|------|
| 不携带验证码登录 | 400 | `验证码不能为空` |
| 验证码错误 | 400 | `验证码错误` |
| 正确验证码 + 正确凭据 | 200 | 返回 JWT，登录成功 |
| 复用同一验证码二次登录 | 400 | `验证码已过期，请刷新`（一次性防重放） |
| 正确验证码 + 错误密码 | 400 | `用户名或密码错误`（验证码校验不误判） |

前端唯一密码登录入口 `Login.vue` 已内置验证码组件（`fetchCaptcha()` 总会设置 `captchaKey`，表单 `captchaCode` 必填校验），无需改动。

## 4. 并发与数据一致性整改

> 共同根因：check-then-act（先查后改）竞态。统一解法：**条件 UPDATE 原子扣减**。

### 4.1 C1 下单扣库存非原子（超卖）

**问题描述**：`if (stock < qty) throw; setStock(stock - qty); updateById` 为读写分离操作，并发时两个事务同时读到库存=1 均通过校验，导致超卖。

**修复方案**：Mapper 层原子扣减，靠受影响行数判断：

```java
// UPDATE product_sku SET stock = stock - #{qty} WHERE id = #{id} AND stock >= #{qty}
if (productSkuMapper.deductStock(sku.getId(), qty) == 0) {
    throw new BusinessException("商品规格库存不足: " + product.getName());
}
```

**验证结果**：`OrderServiceImpl` 已确认使用原子 `deductStock`；商品维度同样处理。

### 4.2 C2 优惠券领取超发

**修复方案**：`couponMapper.deductStock(couponId)` 条件 UPDATE（`WHERE stock > 0`），返回 0 即抢完。

**验证结果**：`UserCouponServiceImpl.java:137` 已确认。

### 4.3 C3 秒杀 DB 库存丢更新

**修复方案**：`seckillSessionMapper.deductStock(sessionId)` 原子扣减。

**验证结果**：`SeckillServiceImpl.java:263` 已确认。

### 4.4 C4 定时任务自调用事务失效

**修复方案**：将 `@Transactional` 方法从定时入口拆离为独立调用路径，避免同 Class 自调用绕过 AOP 代理。

**验证结果**：调用链已确认修正。

## 5. 前端全局缺陷整改

### 5.1 F1 全屏 loading 永久泄漏

**问题描述**：`request.ts` 错误拦截器「无 response」分支与 blob 下载分支均未调用 `hideLoading()`，`requestCount` 只增不减，任一次网络超时/下载后全屏遮罩卡死。

**修复方案**：错误拦截器入口统一 `hideLoading()`；下载分支补 `hideLoading()`。

**验证结果**：代码已确认两个分支均关闭 loading。

### 5.2 F2 Axios 封装类型错位（TS2349）

**问题描述**：`RequestApi` 接口只有方法签名、无调用签名，导致全项目 `request({...})` 调用报 TS2349，并级联产生页面隐式 any 错误。

**修复方案**：为接口补充调用签名，与 `request()` 一致，支持 `request(config)` 与 `request.get(url)` 两种写法。

**验证结果**：全量 TS2349 报错清零，type-check 本项目页面 0 报错。

### 5.3 R1 我的优惠券页运行时白屏

**问题描述**：`MyCoupon.vue` 调用 `getMyCoupons` 但未导入，运行时报 `getMyCoupons is not defined`。

**修复方案**：补充导入 `import { getMyCoupons } from "@/api/eshop/user_coupons"`。

**验证结果**：构建通过，接口调用恢复正常。

## 6. 本次整改新增内容

> 在上一轮高危修复基础上，本次针对「仍可能引发生产事故」的隐患做了专项整改，全部通过编译与实测。

### 6.1 N1 mapper XML namespace 双重包名（9 个文件）

**问题描述**：mapper XML 的 `namespace` 写成 `com.shopsphere.eshop.mapper.com.shopsphere.eshop.mapper.XxxMapper`（包名重复拼接）。当前因未在 XML 中写自定义 SQL 而「侥幸」可启动，一旦添加自定义 SQL 将导致 MyBatis 启动绑定失败。

**修复方案**：9 个文件统一修正为 `com.shopsphere.eshop.mapper.XxxMapper`。

**涉及文件**：`AddressMapper.xml`、`CartMapper.xml`、`FavoriteMapper.xml`、`OrderMapper.xml`、`ProductCommentMapper.xml`、`ProductImageMapper.xml`、`ProductMapper.xml`、`UserMapper.xml`、`VisitLogMapper.xml`

**验证结果**：应用完整启动成功，Mapper 绑定正常，无启动异常。

### 6.2 N2 参数校验不完整

**问题描述**：下单数量 `quantity` 仅 `@NotNull` 无下限（传 0/负数破坏库存逻辑）；商品价格/库存无范围约束；嵌套 `OrderItemDTO` 因缺少 `@Valid` 级联校验实际不生效；`RefundApplyDTO` 误用 `org.jetbrains` 的 `@NotNull`（不参与 Jakarta Validation）；`CartController` 数量参数无校验。

**修复方案**：

| 位置 | 修复内容 |
|------|----------|
| `OrderCreateDTO` | `quantity` 增加 `@Min(1)`；`items` 增加 `@Valid` 级联 |
| `ProductSaveDTO` | `price` 增加 `@DecimalMin("0.01")`；`stock` 增加 `@Min(0)` |
| `RefundApplyDTO` | 注解改为 `jakarta.validation.constraints.NotNull` |
| `MerchantController` | `createProduct`/`updateProduct` 补充 `@Valid` |
| `CartController` | `quantity` 增加 `@Min(1)`（配合 `@Validated`） |
| `CartServiceImpl` | 服务层兜底校验，`quantity < 1` 抛业务异常（双保险，保证任何调用路径均生效） |

**验证结果**：单测 7 项全通过；接口实测 `quantity=0` 被拒绝、`quantity=2` 正常。

### 6.3 N3 越权访问返回 500 而非 403

**问题描述**：`AccessDeniedException`（`@PreAuthorize` 拒绝时抛出）被 `GlobalExceptionHandler` 的 `RuntimeException` 兜底处理成 HTTP 500「服务繁忙」，错误码语义错误，且前端无法区分「无权限」与「服务器故障」。

**修复方案**：新增专门异常处理器：

```java
@ExceptionHandler(AccessDeniedException.class)
public ResponseEntity<Result<?>> handleAccessDeniedException(AccessDeniedException ex) {
    log.warn("权限不足: {}", ex.getMessage());
    return buildResponse(403, "权限不足，无法访问该资源");
}
```

**验证结果**：实测普通用户访问管理接口由 **HTTP 500 修正为 HTTP 403**。

### 6.4 N4 补充最小业务测试集

**问题描述**：`src/test` 仅有一个空的 `contextLoads` 测试，无任何业务断言，无法证明修复有效性。

**修复方案**：新增 `ParamValidationTest`（7 个用例），直接使用 Jakarta Validator 验证 DTO 约束：
- 下单数量 = 0 或缺失 → 拒绝
- 商品价格 ≤ 0 → 拒绝
- 商品库存为负数 → 拒绝
- 合法订单/商品 → 通过
- 退款申请 `orderId` 为空 → 拒绝

**验证结果**：`Tests run: 7, Failures: 0, Errors: 0, Skipped: 0`（0.588s）。

### 6.5 第三阶段质量打磨（Q7 / Q9 / Q11 / Q12 / Q13）

> 在第一、二阶段高危项整改完成后，进一步推进《代码质量改进文档》第三阶段（质量打磨）的落地，本轮完成 5 项。

#### 6.5.1 Q7 秒杀状态魔数 → 常量

- **问题**：`SeckillController` 直接比较 `s.getStatus() == 0 || s.getStatus() == 1`，状态含义不明，且与已有常量类 `SeckillSessionStatus` 脱节。
- **修复**：改为 `SeckillSessionStatus.PENDING / ACTIVE` 常量引用。
- **验证**：编译通过。

#### 6.5.2 Q9 购物车列表 N+1 查询 → 批量查询

- **问题**：`CartServiceImpl.listCart` 对每件商品执行 2 次 `selectById`（商品 + SKU），购物车有 N 件商品即产生 1+2N 次 SQL。
- **修复**：先收集去重后的商品/SKU ID，各执行 1 次 `selectBatchIds`，内存组装（SQL 固定为 3 次）。
- **验证**：编译通过；行为与原逻辑一致（SKU 优先、缺省回退商品维度）。

#### 6.5.3 Q11 删除 TokenUtils 死代码

- **问题**：`TokenUtils` 中 `validateAuthorizationHeader` / `validateToken` / `maskToken` 三个私有方法从未被调用。
- **修复**：删除，类仅保留 `extractToken` / `extractTokenFromRequest`。

## 9. 近期业务逻辑修复记录（v1.2 新增）

> 在 v1.1 安全与并发整改基础上，对系统核心业务规则做了专项走查，发现并修复 **13 项业务逻辑问题**，覆盖金额计算、优惠券状态口径、商品 SKU/评分、商家审核、统计口径等，全部通过编译与接口实测。

### 9.1 金额计算类

#### 9.1.1 B1 折扣券计算错误（8.5 折变 1.5 折）

- **问题**：`OrderServiceImpl` 将 `max_discount`（最高优惠金额上限）直接赋值给实付金额，导致 100 元商品实付变为上限值（约 1.5 折）。
- **修复**：实付 = 总额 × (value/10)；当优惠额超过 `max_discount` 时封顶，实付 = 总额 − 上限：

```java
BigDecimal discountedPay = totalAmount.multiply(coupon.getValue().divide(BigDecimal.valueOf(10)));
if (coupon.getMaxDiscount() != null && coupon.getMaxDiscount().compareTo(BigDecimal.ZERO) > 0) {
    BigDecimal saved = totalAmount.subtract(discountedPay);
    if (saved.compareTo(coupon.getMaxDiscount()) > 0) {
        payAmount = totalAmount.subtract(coupon.getMaxDiscount());
    } else {
        payAmount = discountedPay;
    }
}
```

- **验证**：500 元订单 8.5 折（上限 50）→ 实付 450；200 元 → 170；150 元 → 127.5。

#### 9.1.2 B2 结算页折扣券预览计算错误（前端）

- **问题**：结算页将"折后实付"与"最高优惠金额"混淆比较，任意订单实付恒等于上限（如周年庆券任何订单都变 50 元）。
- **修复**：与后端统一公式——优惠额超上限封顶，实付 = 原价 − 上限。
- **验证**：前后端计算口径一致，各金额档位实测与后端返回一致。

### 9.2 优惠券状态口径类

#### 9.2.1 B3 过期券被误判为"已拥有"

- **问题**：领券/签到/秒杀多处用"用户券记录数"判断是否已领取，已过期/已使用的券仍占领取上限，导致用户无法再领同种券。
- **修复**：统一新增 `countUsable(userId, couponId)`（仅统计未使用且未过期），签到、秒杀、领券中心、我的券四处复用同一口径。

#### 9.2.2 B4 每种券每人领取上限（limitPerUser）

- **问题**：仅秒杀场次有自身限购，普通券的 `limitPerUser` 未在各渠道发券前强制校验。
- **修复**：所有发券路径（普通领取 / 签到里程碑 / 节日活动 / 秒杀）统一校验"已持有数 ≥ limitPerUser 即拒绝"。

#### 9.2.3 B5 领券中心上限提示优化

- **问题**：达到上限后仍显示"立即领取"，点击才弹"已达到领取上限"。
- **修复**：`/available` 接口新增 `claimedCount` 字段，达到上限直接显示"已领取"并禁用按钮，无需再请求后端。

### 9.3 商品与商家类

#### 9.3.1 B6 商家审核提交被拦截

- **问题**：`submitApply` 拦截"待审核或已通过"记录，已拒绝用户无法重新申请；`getMyApply` 用 `selectOne` 遇多条历史记录报错。

#### 9.3.2 B7 商品评分计算错误
