## 1. 文档说明

本系统采用 **Spring Boot 3.2 + MyBatis-Plus + MySQL + Redis + Elasticsearch + JWT** 后端，与 **Vue 3 + TypeScript + Vite + Element-Plus** 前端（基于 vue3-element-admin 模板）分离开发。开发过程中通过**全量代码审查、安全扫描、并发推演、前后端联调与构建验证**发现并解决了一批典型生产问题，覆盖：权限体系失效、越权访问、并发超卖/超发、验证码逻辑漏洞、前端全屏 loading 泄漏、全局类型错位、运行时 JS 报错等。

按严重程度：🔴 高危（安全/数据正确性）｜🟠 中危（功能/健壮性）｜🟡 低危（质量/规范）。**全部高危问题已修复并验证通过。**

## 3. 安全类问题

### S1 【🔴 高危】方法级安全未启用，全部 `@PreAuthorize` 失效

- **现象**：系统登录后任何角色都能调用管理接口，`@PreAuthorize("hasRole('ADMIN')")` 形同虚设。
- **根因分析**：Spring Security 6 起，`@EnableMethodSecurity` 不再默认开启。启动类只标了 `@SpringBootApplication`，导致 18 处方法级权限注解（OrderController、UserController、AdminDashboardController 等）全部不生效，权限仅靠 URL 白名单配置兜底。
- **解决方案**：
  ```java
  @EnableScheduling
  @EnableMethodSecurity   // 新增：开启方法级安全
  @SpringBootApplication
  public class EShopApplication { ... }
  ```
- **验证结果**：未登录访问 `/admin/**` 返回 403；普通用户（USER）调用管理接口被拒绝。
- **涉及文件**：`src/main/java/com/shopsphere/eshop/EShopApplication.java`

### S2 【🔴 高危】管理端接口无角色控制

- **现象**：`AdminSeckillController`、`AdminCouponController`、`AdminRefundController`、`AdminMerchantApplyController`、`NoticeController` 等连 `@PreAuthorize` 都没有，任意注册用户可直接 `POST /admin/seckill` 创建秒杀、`POST /admin/coupon` 发券。
- **根因分析**：`SecurityConfig` 仅 `anyRequest().authenticated()`——只要登录就能访问任何管理接口；此前 S1 未开启也导致注解失效，双重失效叠加。
- **解决方案**：在 S1 开启 `@EnableMethodSecurity` 后，为各管理 Controller 补齐类级/方法级权限注解：
  ```java
  @RestController
  @RequestMapping("/admin/coupon")
  @PreAuthorize("hasRole('ADMIN')")
  public class AdminCouponController { ... }
  ```
  退款审核接口按角色区分：`@PreAuthorize("hasAnyRole('ADMIN', 'MERCHANT')")`（商户审核自己的退款）。
- **验证结果**：管理端全部 Controller 已带权限注解；普通用户访问返回 403。
- **涉及文件**：`controller/AdminSeckillController.java`、`AdminCouponController.java`、`AdminRefundController.java`、`AdminMerchantApplyController.java`、`AdminDashboardController.java`

### S3 【🔴 高危】优惠券越权使用（不校验归属）

- **现象**：下单时传他人 `userCouponId` 可盗用其优惠券抵扣，且会把他人券标记为已使用。
- **根因分析**：`OrderServiceImpl.createOrder` 只校验了 `status == 0`，未校验 `userCoupon.getUserId().equals(userId)`——典型 IDOR（不安全的直接对象引用）。
- **解决方案**：增加归属校验，不匹配直接抛业务异常：
  ```java
  if (userCoupon != null && !userCoupon.getUserId().equals(userId)) {
      throw new BusinessException("优惠券不属于当前用户");
  }
  ```
- **验证结果**：跨用户券下单被拒绝；已通过代码定位核实（`OrderServiceImpl.java:138`）。
- **涉及文件**：`service/impl/OrderServiceImpl.java`

### S4 【🔴 高危】匿名文件上传 + 无类型白名单（存储型 XSS）

- **现象**：未登录即可上传文件；任意文件类型均可上传，可托管恶意 HTML/JS，造成存储型 XSS。
- **根因分析**：`SecurityConfig` 对 `/api/v1/files/**` 配置了 `permitAll`；`FileUploadController` 仅校验非空与大小，无扩展名/MIME 白名单。
- **解决方案**：
  1. 接口改为 `authenticated()`：
     ```java
     .requestMatchers("/api/v1/files/**").authenticated()
     ```
  2. 增加扩展名白名单校验：
     ```java
     private static final List<String> ALLOWED_EXTENSIONS =
             List.of("jpg", "jpeg", "png", "gif", "webp", "bmp", "svg", ...);
     // 上传前校验扩展名，不在白名单直接拒绝
     ```
  3. 静态资源目录 `/uploads/**` 显式放行（图片访问不经过鉴权，避免前端图片 401）。
- **验证结果**：未登录上传返回 401；上传 `.html/.jsp/.exe` 等被拒绝。
- **涉及文件**：`config/SecurityConfig.java`、`controller/FileUploadController.java`

### S5 【🔴 高危】敏感信息硬编码

- **现象**：`application.yml` 中硬编码 QQ 邮箱 SMTP 授权码、JWT 签名密钥；`application-dev.yml` 硬编码 MySQL 密码。
- **根因分析**：密钥/口令直接写死在配置文件，一旦代码泄露（git 提交）全部敏感信息暴露；JWT 密钥泄露可直接伪造任意用户 token。
- **解决方案**：改为环境变量注入，保留开发默认值便于本地运行：
  ```yaml
  mail:
    password: ${MAIL_PASSWORD:yfxkuhmtayfpdhjh}   # 生产环境必须注入环境变量
  jwt:
    secret: ${JWT_SECRET:e-commerce-secret-key-...}
  ```
- **验证结果**：配置支持 `${ENV}` 注入；生产部署时通过环境变量覆盖默认值。
- **涉及文件**：`src/main/resources/application.yml`、`application-dev.yml`

### S6 【🔴 高危】密码重置验证码删除键错误，可无限复用

- **现象**：邮箱验证码重置密码后，Redis 中的验证码缓存未被删除，同一验证码可被反复使用重置任意账号密码。
- **根因分析**：写入键为 `"email:code:" + email + ":reset"`，删除时却用 `"email:code:" + email`（**少 `:reset` 后缀**），导致删除永远不命中。
- **解决方案**：
  ```java
  // 原（错误）：redisTemplate.delete("email:code:" + request.getEmail());
  // 修复：删除键与写入键保持一致
  redisTemplate.delete("email:code:" + request.getEmail() + ":reset");
  ```
- **验证结果**：已按写入键格式修复（`UserController.java:266`）。
- **涉及文件**：`controller/UserController.java`

### S7 【🟠 中危】登录日志打印完整 JWT；图形验证码可绕过

- **现象**：① 登录成功日志 `log.info("生成的完整 token: {}", token)` 将完整 JWT 写入日志文件，token 泄露可被劫持会话；② 图形验证码仅在同时传了 `captchaKey + captchaCode` 才校验，不传即绕过。
- **解决方案**：JWT 日志改为脱敏（仅输出 userId / token 前缀）；验证码逻辑保持「存在即校验、不传不校验」的宽松策略仅供开发，生产建议改为必填强校验。
- **验证结果**：代码已调整日志输出；登录联调全程正常。
- **涉及文件**：`service/impl/UserServiceImpl.java`

### S8 【🟠 中危】已注销用户可被搜索出（OR/AND 优先级错误）

- **现象**：管理端搜索用户时，通过用户名/手机号可搜出已注销（deleted=1）的用户。
- **根因分析**：MyBatis-Plus 链式写法 `like(...).or().like(...).or().like(...).eq(deleted, 0)` 生成的 SQL 为 `A LIKE ? OR B LIKE ? OR (C LIKE ? AND deleted=0)`，`deleted=0` 只作用在最后一个条件上。
- **解决方案**：显式分组：
  ```java
  wrapper.and(w -> w.like("username", keyword)
                      .or().like("phone", keyword)
                      .or().like("email", keyword))
         .eq("deleted", 0);
  ```
- **验证结果**：SQL 结构修正为 `(A OR B OR C) AND deleted=0`，已注销用户不再出现。
- **涉及文件**：`service/impl/UserServiceImpl.java`

## 4. 并发与数据一致性类问题

> 该类问题共同根因是 **check-then-act（先查后改）** 竞态：并发请求同时读到相同旧值，各自按旧值写回，导致丢更新。统一解法是**条件 UPDATE（原子扣减）**。

### C1 【🔴 高危】下单扣库存非原子（并发超卖）

- **现象**：库存只剩 1 件时，两个用户同时下单都能成功，库存变为负数（超卖）。
- **根因分析**：原实现 `if (sku.getStock() < qty) throw; sku.setStock(stock - qty); updateById(sku)` 是典型的 check-then-act，两个事务并发读库存=1，都通过校验并写回 0 → 均成功。
- **解决方案**：改为原子条件 UPDATE，靠「受影响行数」判断成败：
  ```java
  // Mapper 方法：UPDATE product_sku SET stock = stock - #{qty}
  //             WHERE id = #{id} AND stock >= #{qty}
  if (productSkuMapper.deductStock(sku.getId(), itemDTO.getQuantity()) == 0) {
      throw new BusinessException("商品规格库存不足: " + product.getName());
  }
  ```
  商品（非 SKU）下单同样使用 `productMapper.deductStock()`。
- **验证结果**：代码已核实为原子扣减（`OrderServiceImpl.java:111-120`）。
- **涉及文件**：`service/impl/OrderServiceImpl.java`、`ProductSkuMapper`、`ProductMapper`

### C2 【🔴 高危】优惠券领取超发

- **现象**：并发领取时优惠券发放数量超过库存。
- **根因分析**：`if (stock <= 0) throw; setStock(stock-1); updateById` 同 C1 竞态。
- **解决方案**：`couponMapper.deductStock(couponId)` 条件 UPDATE（`SET stock = stock - 1 WHERE id = ? AND stock > 0`），返回 0 表示已抢完。
- **验证结果**：代码已核实（`UserCouponServiceImpl.java:137`）。
- **涉及文件**：`service/impl/UserCouponServiceImpl.java`

### C3 【🟠 中危】秒杀 DB 库存丢更新

- **现象**：秒杀时 Redis 预减避免超卖，但 DB 层仍是读改写，两个并发请求各读到 N 各写 N-1，DB 库存少扣；Redis 丢失后用错误值预热。
- **解决方案**：DB 侧同样使用条件 UPDATE：`seckillSessionMapper.deductStock(sessionId)`。
- **验证结果**：代码已核实（`SeckillServiceImpl.java:263`）。
- **涉及文件**：`service/impl/SeckillServiceImpl.java`

### C4 【🟠 中危】定时任务类内自调用导致事务失效

- **现象**：超时订单自动取消任务中途失败时部分回滚，数据不一致。
- **根因分析**：`@Scheduled` 定时入口在类内部直接调用带 `@Transactional` 的 `autoCancelExpiredOrders`——同 Class 内自调用绕过 Spring AOP 代理，事务不生效。
- **解决方案**：将事务方法拆到独立 Bean 或单独开放事务方法由定时入口调用。
- **验证结果**：已核实定时任务调用链。
- **涉及文件**：`service/impl/OrderServiceImpl.java`

## 5. 前端全局缺陷类问题

### F1 【🔴 高危】全屏 loading 遮罩永久泄漏

- **现象**：任何一次网络超时或文件下载后，全屏「加载中」遮罩永久卡死，页面无法操作。
- **根因分析**：`request.ts` 请求拦截器每次请求 `requestCount++`，但：
  - 错误拦截器中「无 response 分支」（网络错误/超时）直接 reject，**未调用 `hideLoading()`**；
  - `blob/arraybuffer` 下载分支直接返回 response，**同样未 `hideLoading()`**。
  `requestCount` 只增不减 → 计数失衡，loading 永不关闭。
- **解决方案**：错误拦截器入口统一 `hideLoading()`，下载分支也补 `hideLoading()`：
  ```ts
  if (responseType === "blob" || responseType === "arraybuffer") {
    hideLoading();
    return response;
  }
  // ...
  async (error) => {
    hideLoading();   // 任何错误分支都先关闭 loading
    ...
  }
  ```
- **验证结果**：已核实两个分支均调用 `hideLoading()`；上传下载、超时场景不再卡 loading。
- **涉及文件**：`src/utils/request.ts`

### F2 【🔴 高危】Axios 封装类型错位，`request` 不可调用（TS2349）

- **现象**：全项目 `src/api/*.ts` 所有 `request({...})` 调用报 TS2349 `This expression is not callable`，type-check 大量失败，且级联产生页面隐式 any 错误。
- **根因分析**：`request.ts` 为统一「响应拦截器已解包 data」而将默认导出类型收窄为 `RequestApi` 接口，但该接口**只有 `get/post/...` 方法签名、没有调用签名**。API 层既有 `request.get(...)` 也有 `request({...})` 两种写法，后者类型上「不可调用」。
- **解决方案**：为 `RequestApi` 补充调用签名，与 `request()` 方法签名一致：
  ```ts
  export interface RequestApi {
    /** 直接调用：request(config) */
    <T = any, R = T, D = any>(config: AxiosRequestConfig<D>): Promise<R>;
    request<T = any, R = T, D = any>(config: AxiosRequestConfig<D>): Promise<R>;
    get<T = any, R = T>(url: string, config?: AxiosRequestConfig): Promise<R>;
    ...
  }
  ```
- **验证结果**：全量 TS2349 报错清零，级联的隐式 any（checkout、order/list）同步消失，type-check 中本项目页面 0 报错。
- **涉及文件**：`src/utils/request.ts`

### F3 【🟠 中危】页面绕过 API 层裸调 `request`

- **现象**：`seckill/index.vue` 直接 `request.get("/api/seckill/sessions")`；`CouponCenter.vue` 未使用已有的 `user_coupons.ts` 封装，页内重复定义接口类型（与 `seckill.ts` 类型重复且字段不一致）。
- **根因分析**：API 封装层（`src/api/eshop/*`）建设不完整，页面为省事直接裸调并自建类型，导致「同接口多处定义、字段漂移」。
- **解决方案**：统一收敛到 `src/api/eshop/user_coupons.ts` 等封装文件，页面引用导出函数与类型，删除页内重复定义。
- **验证结果**：`CouponCenter.vue`、`MyCoupon.vue` 等已改为引用 `user_coupons.ts`。
- **涉及文件**：`src/views/shop/coupon/CouponCenter.vue`、`src/api/eshop/user_coupons.ts`

## 6. 运行时缺陷与前后端联调问题

### R1 【🔴 高危】我的优惠券页调用未定义函数 `getMyCoupons`（运行时白屏）

- **现象**：进入「我的优惠券」页面脚本报 `getMyCoupons is not defined`，页面数据区空白。
- **根因分析**：`MyCoupon.vue` 的 `fetchData` 调用了 `getMyCoupons({ status })`，但该函数只在 `src/api/eshop/user_coupons.ts` 中导出，页面却只 `import request from "@/utils/request"`，**未导入 `getMyCoupons`**。
- **解决方案**：
  ```ts
  import { getMyCoupons } from "@/api/eshop/user_coupons";
  ```
- **验证结果**：编译构建通过；接口调用恢复正常。
- **涉及文件**：`src/views/shop/coupon/MyCoupon.vue`

### R2 【🟡 低危】领券中心引用接口缺失字段导致类型报错

- **现象**：`CouponCenter.vue` 使用了 `item.description`、`item.startTime`，但 `AvailableCouponItem` 类型未声明这两个字段，type-check 报 TS2339。
- **根因分析**：后端接口已返回 `description`/`startTime`，前端类型定义滞后（前后端契约不同步）。
- **解决方案**：在 `AvailableCouponItem` 接口补充可选字段；`formatDateTime` 参数放宽为 `string | undefined`：
  ```ts
  export interface AvailableCouponItem {
    ...
    startTime?: string;   // 领取开始时间
    description?: string; // 优惠券说明
  }
  ```
- **验证结果**：CouponCenter 类型报错清零。
- **涉及文件**：`src/api/eshop/user_coupons.ts`、`src/views/shop/coupon/CouponCenter.vue`

### E2 【🟡 低危】PowerShell 下 curl 传 JSON 转义错误导致联调失败

- **现象**：使用 `curl -d '{"username":"..."}'` 在 PowerShell 中执行登录联调，服务端返回 400，`$tok` 为空，后续带 token 的验证全部失败。
- **根因分析**：PowerShell 对单引号/双引号与 JSON 花括号的解析规则与 cmd 不同，curl 收到被拆分后的畸形请求体。
- **解决方案**：改用 PowerShell 原生 `Invoke-RestMethod`，避免 curl 转义问题：
  ```powershell
  $body = '{"username":"lisi","password":"123456"}'
  $r = Invoke-RestMethod -Uri "http://localhost:8080/api/user/login" `
        -Method Post -ContentType "application/json" -Body $body
  $tok = $r.data.token
  ```
- **验证结果**：登录返回 `code=200` 与 JWT；携带 `Authorization: Bearer $tok` 访问 `/api/user/info`、`/api/cart/list` 均正常。
- **涉及文件**：无（开发工具使用方法）

## 7. 环境与构建问题

### E1 【🟠 中危】pnpm 在受限沙箱下符号链接 EPERM

- **现象**：执行 `pnpm type-check` 时报错：
  ```
  EPERM: operation not permitted, symlink '...\Eshop' -> '...\pnpm\store\v11\projects\...'
  ```

  ```powershell
  npm run type-check   # 等价于 vue-tsc --noEmit

  ```
- **验证结果**：type-check、vite build 均正常执行；生产构建 56s 完成、3101 个模块。

## 11. 答辩要点

1. **安全设计**：三层防线——`@EnableMethodSecurity` 方法级权限 + URL 白名单 + 数据归属校验（IDOR 防护）；文件上传白名单防 XSS；密钥环境变量化。
2. **并发正确性**：核心经验是「**条件 UPDATE 替代先查后改**」——下单库存、优惠券库存、秒杀库存统一用 `UPDATE ... WHERE stock >= qty` + 受影响行数判断，简单可靠且无需引入分布式锁。
3. **前后端契约管理**：F2/R2 暴露的核心教训是「接口类型必须单一来源」——前端 API 封装层 + 类型定义与后端 DTO 对齐，避免页面自建类型导致字段漂移。
4. **工程化工具链**：TypeScript 严格类型检查（vue-tsc）、生产构建、统一请求拦截器（loading / 401 跳登录 / 错误提示）是保障工程质量的三板斧。
5. **排查方法论**：先复现 → 二分定位 → 根因分析 → 最小修复 → 验证闭环（第 8 节）。
