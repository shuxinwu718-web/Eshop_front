## 一、模块概述

平台营销活动模块用于活跃用户、促进转化。管理员在后台创建"任务型"活动（签到 / 下单 / 收藏达标后发放优惠券奖励），用户在活动中心页查看活动、实时进度并领取奖励。

设计要点：

- **通用任务制**：任务类型可扩展（当前支持签到天数、已支付订单数、收藏商品数），后续新增类型只需扩展 `TASK_TYPES` 与进度计算分支。
- **奖励统一走优惠券**：复用现有 `UserCouponService.grantCoupon` 直发管道，不扣优惠券库存、不查限领数量（营销奖励不受日常限领约束）。
- **防重设计**：`user_activity_record` 表按 `(user_id, activity_id, task_id, source=MARKETING)` 防重，同一任务每人仅可领取一次。
- **进度实时计算**：进度不落库，按活动起止时间范围实时统计，保证数据一致，避免定时任务对账。

## 三、数据模型设计

### 3.1 `marketing_activity`（营销活动主表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | 自增 |
| activity_name | varchar(100) | 活动名称 |
| activity_icon | varchar(50) | 活动图标（emoji） |
| description | varchar(500) | 活动说明 |
| start_time / end_time | datetime | 活动起止时间 |
| status | tinyint | 0 停用 / 1 启用 |
| sort_order | int | 排序（越小越靠前） |
| deleted | tinyint | 逻辑删除 |

索引：`idx_status`、`idx_time_range(start_time, end_time)`

### 3.2 `marketing_task`（活动任务表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | 自增 |
| activity_id | bigint | 所属活动 ID |
| task_type | varchar(30) | SIGNIN_DAYS-累计签到 / ORDER_COUNT-已支付订单 / COLLECT_COUNT-收藏商品 |
| task_name | varchar(100) | 任务名称 |
| target_value | int | 目标值（如签到 5 天 / 下单 3 笔 / 收藏 2 件） |
| reward_coupon_id | bigint | 奖励优惠券 ID |
| reward_icon | varchar(50) | 奖励展示图标（emoji） |
| sort_order | int | 排序 |

索引：`idx_activity_id`

### 3.3 `user_activity_record`（用户活动领取流水，兼容旧表）

- 复用既有表，新增列 `task_id`（营销任务防重）+ 组合索引 `idx_user_task(user_id, activity_id, task_id)`
- `source` 区分来源：ACTIVITY（活动领取）/ SIGNIN（签到）/ LOTTERY（抽奖）/ MARKETING（营销活动）
- **兼容旧库**：MySQL 8.0 不支持 `ADD COLUMN IF NOT EXISTS`，脚本用存储过程做条件 DDL，可重复执行、幂等

## 四、后端实现

### 4.1 接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/page` | 分页查询（keyword / status） |
| GET | `/{id}` | 活动详情 |
| POST | `` | 新增活动（含任务列表） |
| PUT | `` | 编辑活动（任务整体重建） |
| PUT | `/status/{id}` | 启用/停用 |
| DELETE | `/{id}` | 删除活动及任务 |

**用户端 `MarketingActivityController`**（前缀 `/api/marketing-activity`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/active` | 进行中活动列表（`@CurrentUserId` 可选，游客无进度） |
| GET | `/{id}` | 活动详情（含任务与用户进度） |
| POST | `/{activityId}/claim/{taskId}` | 领取任务奖励 |

安全放行：`SecurityConfig` 中 `GET /api/marketing-activity/**` 免登录，领取必须登录。

### 4.2 核心逻辑

**任务进度计算 `calcTaskProgress`**（按活动起止时间范围实时统计）：

| 任务类型 | 统计口径 |
|---|---|
| SIGNIN_DAYS | `user_signin_record` 中 sign_date 落在 `[start.toLocalDate(), end.toLocalDate()]`，按日去重计数 |
| ORDER_COUNT | `order` 中 pay_status=1 且 create_time 落在区间内 |
| COLLECT_COUNT | `favorite` 中 create_time 落在区间内 |

**领取流程 `claimReward`**：

1. 校验活动存在、启用、处于进行中
2. 校验任务属于该活动
3. 防重：查 `user_activity_record`（user_id + activity_id + task_id + MARKETING）已领取则拒绝
4. 进度校验：currentValue < targetValue 则拒绝（提示当前进度）
5. 发放奖励：`userCouponService.grantCoupon(userId, rewardCouponId)` 直发
6. 写领取流水（含 task_id），事务包裹

**任务状态 `taskStatus`**：0 未达成 / 1 可领取 / 2 已领取；活动 `timeStatus`：0 未开始 / 1 进行中 / 2 已结束。

**N+1 规避**：`toActivityVOs` 批量查任务、`selectBatchIds` 批量查奖励券、一次批量查用户已领记录，内存组装，避免逐活动逐任务查询。

## 五、前端实现

- 列表页：搜索（名称/状态）、表格（活动图标+名称、说明、任务数、活动时间、状态 switch、创建时间、编辑/删除）、分页

## 八、遗留与后续建议

1. **任务类型扩展**：新增类型时需同步扩展后端 `TASK_TYPES` + `calcTaskProgress` 分支，及前端任务类型下拉选项。
2. **并发领取**：防重依赖数据库查询 + 事务，极端并发下理论上可能双发；后续可在 `user_activity_record` 上加唯一索引（user_id, activity_id, task_id）做兜底。
3. **活动参与门槛**：当前未限制活动参与资格（如会员等级、新老用户），如需可按用户属性扩展校验。
4. **后续新模块意向**：店铺主页装修（待规划）。
