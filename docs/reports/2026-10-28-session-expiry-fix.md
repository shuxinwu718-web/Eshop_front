## 1. 问题来源及调查范围

项目所有者从系统访问日志发现大量 HTTP 403，怀疑用户 token 过期后页面没有自动退出，后台请求仍在发送，需要手动刷新才能更新登录状态。

本次先审阅前端指定分支，再核对后端认证过滤器、安全配置与 SSE 连接逻辑，使用隔离测试和本地浏览器模拟验证。没有读取生产访问日志，没有在生产站点创建订单、支付、退款或更改账号。因此，本报告确认的是代码中的失效处理缺陷及修复结果，不能断言历史所有 403 都是 token 过期导致。权限不足本来就应产生 403。

此前基于 `master` 的审阅不作为本次修复基线；本次已重新核对指定分支。

## 2. 原因分析

### 2.1 公开页面将“登录失效”误当成“游客操作”

原请求拦截器使用 `!hasToken || isPublicRoute` 判断是否只提示错误。在首页、商品详情等公开页面，即使用户携带失效 token，收到 401/403 后也只弹提示，不清 token、不清资料缓存，页面仍可能显示已登录。

### 2.2 登录状态不是统一的响应式数据

原 `isLoggedIn()` 仅检查浏览器存储中是否存在 token，不检查过期时间。组件通过 `computed` 包装存储读取，存储本身不产生 Vue 响应式通知，因而删除 token 后，头像、角色入口和轮询条件不一定同步更新。

用户资料还有内存及本地缓存；缓存命中不代表服务器仍认可当前会话。

### 2.3 轮询放大了失效请求

桌面商城未读客服消息每 10 秒查询，通知未读数每 30 秒查询。失效登录态不清理时，仅这两项就可能产生约 480 次失败请求/小时/标签页。商家中心也有定时查询。

这个数字是代码周期推算，不是生产压测或访问日志统计结果。

### 2.4 后端认证与授权响应没有统一区分

普通 JWT 过期或无效时，过滤器原来验证失败后继续执行，没有明确的认证错误响应契约；安全入口也未显式配置未认证 JSON 响应。另一方面，会话被替换明确返回 401，真正无权限返回 403。混用会使前端难以可靠决定是否退出。

### 2.5 长连接与独立 AI 请求没有共同的会话生命周期

通知 SSE 原错误处理不清登录态；token 无效事件和一般网络异常没有清晰区分。AI 流式对话使用独立 `fetch`，不经过主 Axios 拦截器，退出时也缺少统一取消。

客服页面还将函数 `isLoggedIn` 当布尔值使用，漏了 `()`，游客判断不能按预期执行。

## 3. 整改目标与范围

目标是让 UI、持久化存储、路由、轮询和流连接共同遵循一份会话状态：认证失效能自动结束；权限不足和服务异常不会误退出；旧请求不能破坏新登录。

本次涉及认证、会话、相关轮询/SSE/AI 流及测试。不修改交易金额、购物车规格、地址选择、页面重设计、AI 模型配置或数据库结构。不增加 refresh token，不自动延长用户登录时间。

## 4. 解决方案与实际实现

### 4.1 认证响应契约

| 场景 | HTTP / 事件 | 前端处理 |
| --- | --- | --- |
| 无凭据访问受保护接口 | 401，`AUTH_REQUIRED` | 游客只提示需要登录，不反复执行全局退出 |
| JWT 过期 | 401，`TOKEN_EXPIRED` | 清理关联会话 |
| JWT 无效 | 401，`TOKEN_INVALID` | 清理关联会话 |
| 会话版本失效，如异地登录 | 401，`SESSION_REPLACED` | 清理关联会话 |
| 已认证但无权限 | 403 | 提示无权限，保留登录 |
| HTTP 200 但主后端业务码为 401 | 业务认证失败 | 兼容处理，清理关联会话 |
| HTTP 200 但主后端业务码为 403 | 业务权限不足 | 提示无权限，保留登录 |
| 断网、500 等异常 | 网络/服务异常 | 保留登录，不伪装成认证失效 |
| 通知 SSE 的认证失效 | `event: auth-expired` | 主动关连接，清理会话 |
| AI 供应商 key 无效或 AI 服务不可用 | AI 错误 | 只影响 AI；不退出商城账号 |

后端配置 `AuthenticationEntryPoint` 和 `AccessDeniedHandler`，分别输出 JSON 401/403。JWT 认证失败后，公开接口仍可按游客放行；受保护接口由安全入口拒绝。MVC 层既有的权限不足处理继续返回 403。

AI 服务只有明确返回商城用户认证错误标识（`TOKEN_EXPIRED`、`TOKEN_INVALID`、`SESSION_REPLACED`）的 HTTP 401，才触发商城会话失效；普通供应商 401 不触发。此次没有修改独立 Python AI 服务，实际能否提供这些标识取决于该服务的接口实现。

### 4.2 统一响应式会话

新增 `src/utils/session.ts`：维护响应式 token，兼容原有“记住我”的持久化方式；登录、退出、过期清理都通过同一入口更新状态。

依据 JWT `exp` 安排到期清理，并在窗口恢复焦点、页面恢复可见及发送主后端请求前复查。浏览器休眠或后台节流时，定时器不保证精确到毫秒；恢复可见后会补查。前端解码 `exp` 只用于交互和减少无效请求，不替代服务器签名校验与权限验证。

用户资料首次恢复必须经过服务器验证，本地缓存不再作为会话有效的凭据。正在获取资料时若会话改变，旧资料不会写回新会话。

### 4.3 单次失效清理与异步隔离

失效入口先匹配“请求发出时的 token”与“当前 token”。仅当前会话可被清理，同一会话的并发失败只触发一次清理与提示。

清理内容包括 token、用户资料/角色缓存、路由加载标记、相关 SSE 资源和正在进行的认证请求。请求使用 AbortController 取消，响应处理再次检查会话是否已变化，以防旧 401 把新登录退出，或旧成功响应写回旧用户数据。

SSE 同样检查连接实例，迟到的旧连接事件不能关闭新连接。全局连接对象保留稳定引用以便重新登录后恢复订阅。

### 4.4 页面行为与轮询控制

- 在公开页面失效：变为游客，继续浏览，不强迫进入登录页。
- 在受保护页面失效：使用替换导航进入登录页，并保存原页面返回路径。
- 主动退出：原退出流程继续生效，并通知同会话的其他标签页。
- 商城通知轮询在退出时停止；桌面消息轮询依靠响应式登录状态停止；商家定时回调增加实时登录判断，离开布局时销毁定时器。
- 服务或网络异常导致用户资料获取失败时，不再无条件清掉有效登录；受保护导航取消，保留后续重试机会。

### 4.5 多标签页

通过 storage 事件发送同会话退出通知，消息仅含关联摘要、原因和时间，不包含 token、密码或用户资料。只结束匹配的会话，不广播登录凭据，不强制覆盖其他独立登录会话。

另一个标签页已保存新会话时，旧标签页退出不会删除新会话的持久化凭据。跨标签通知不可用时，本标签清理仍会完成；其他标签的服务端请求和过期检查仍是兜底。

### 4.6 通知 SSE

后端在连接建立时验证 JWT 和会话版本；无效时发送明确的 `auth-expired` 事件并关闭，不注册正常连接。对已建立的连接，每 5 秒检查到期时间和会话版本，发现过期或被替换时通知并完成连接。生命周期回调取消对应检查任务。

前端只将明确的认证事件视为退出依据；普通断流主动关闭旧 EventSource，并按 1、2、4……最多 30 秒退避重连，不将断网直接等同于登录失效。重新登录时重新初始化全局 SSE 服务。

该后端仍沿用项目原有单实例、内存保存 SSE 连接的设计。每连接增加会话版本检查，带来 Redis 读取开销；本次未进行大量长连接压测。多实例推送与大规模连接优化不在本次范围内。

### 4.7 AI 流式会话

修复游客判断；为流式请求绑定会话取消信号，退出、切换会话或离开客服页面时取消。取消后不再把迟到片段或错误回调写入原对话，退出时清理该页会话历史。

保留 AI 服务独立的错误语义，不将项目所有者已说明的模型 API key 失效当作商城登录失效。

### 7.1 日志核对方法

验收前后选取相同操作时段，按接口分组统计 401/403，不只看全站总数。重点检查 `/api/v1/chat/unread-count`、通知未读接口及 SSE 连接。

- 到期后可能出现一次或少量 401，随后需要登录的轮询应停止。
- 真正无权限产生的 403 必须保留，不应为了日志好看改成 200。
- SSE 认证失效通过 200 流响应内的 `auth-expired` 事件表示，不能只看其 HTTP 状态判断正常。
- 不记录完整 token、密码；如需将现象写入毕设，使用接口名、时间、状态、脱敏截图和观察结论。

## 8. 部署、兼容性及回退
