## 一、本次改动带来的性能收益

| 改动点 | 收益 | 量化 |
|---|---|---|
| **工具返回瘦身**（去掉 coverImage 长 URL、镜像 URL、截断 description） | 返给 LLM 的 token 显著减少 | 单条工具 JSON 可下降 30%~50% |
| **超时收窄** `TIMEOUT 5s → 3s` | 后端慢/挂时快速失败，缩短最坏等待 | 最坏单工具 5s → 3s |
| **vector 只构建一次**（retriever 懒加载 + 内存缓存，原有） | 每次请求省一次全量 embedding 调用 | 节省时间 + 通义额度 |
| **工具结果回传截断 2000 字符** | 防止超长数据拉高上下文 | 保响应不膨胀 |
| **减少冗余字段返回**（秒杀只留关键信息） | 上下文更紧凑，LLM 更聚焦 | 间接提升准确率 |

## 二、可进一步优化的方向（建议分级）

### P0 · 影响最大，建议优先做
1. **后端新增"性价比推荐"接口**
   现状：AI 在工具层做"评分门槛 + 排序组合"，是**前端二次过滤**。
   优化：后端 `SELECT ... ORDER BY rating DESC, price ASC LIMIT n` 直接返回"高评分且低价"商品，AI 一次拿到即可，少一轮数据搬运、更准。
   预计：推荐准确率提升、减少工具端过滤逻辑。

2. **RAG 检索缓存 + 降级**
   现状：`retrieve()` 每次请求都对用户问题做一次 embedding（联网调用）。
   优化：在 `main.py` 对"同一意图"做短 TTL 的 embedding 结果缓存（如 5 分钟内相同问题直接命中缓存）。
   预计：命中缓存时省一次联网 embedding，P95 延迟下降最高可达 40%。

3. **并行 vs 串行冒险的取舍**：工具调用**必须串行**（要定位到 id 才能查详情），天然上限。若要更快，可考虑 `search_products` 一次返回做富数据，减少二次 `get_product_detail`。

### P1 · 成本/体验均衡
4. **模型降档/温度控制**：`MODEL_NAME` 目前默认 `qwen-turbo`；对"推荐/查询"这类结构化任务，可显式设 `temperature=0.2` 提高确定性、减少废话 token。
5. **历史窗口剪枝**：现在保留最近 10 轮；对纯商品查询类对话，可减少历史注入，进一步省 token。

## 三、性能/安全基线建议（可加监控）

| 指标 | 建议值 | 说明 |
|---|---|---|
| 单请求 LLM 调用次数 | ≤ MAX_TOOL_ROUNDS=3 | 防止模型陷入工具循环 |
| 单用户输入长度 | ≤200 字符 | main.py 已强制 |
| IP 限流 | 10 条/分钟 | 已有 |
| 单工具超时 | ≤3s | 已收窄 |
| 工具结果回传 | ≤2000 字符 | 已截断 |

## 四、一句话总结

本次整改在**不改后端、不加钱加设备**的前提下，通过 **prompt 职责重定位 + 工具参数化（好评门槛/价格排序）+ 返回瘦身 + 超时收窄 + 注入防护**，直接改善"推荐模糊"体验、降低单请求 token 与延迟，并堵住输入注入面。如果需要量化的吞吐压测或深入优化（例：接 Prometheus 统计调用次数/耗时），可作为下一阶段独立任务专项推进。
