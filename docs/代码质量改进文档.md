## 1. 总体结论

系统功能完整（下单/支付/退款/秒杀/优惠券/签到/通知全链路可用），架构分层清晰（Controller → Service → Mapper），前端基于成熟模板（vue3-element-admin）工程质量整体合格。但存在以下系统性风险：

- **后端**：权限体系**实际未生效**（`@PreAuthorize` 全部失效），库存/优惠券扣减存在并发超卖隐患，数个高危越权与安全漏洞。
- **前端**：Axios 封装存在 loading 泄漏与类型错位两个全局性缺陷，页面层大量重复代码、超大组件。

> 以上风险已于 2026-08-06 ~ 08-07 完成整改（详见各条目标记），后续问题为质量打磨与测试扩展。

## 2. 后端安全问题（高危，答辩必问）

> **整改状态**：S1-S6、S8 已修复 ✅；S7 部分修复（JWT 日志已脱敏 ✅，验证码可绕过 ⏳ 待整改）。

### S1 【致命】方法级安全未启用，全部 `@PreAuthorize` 失效 【✅ 已整改】

- **位置**：`e:\idea_workspase\e-shop\src\main\java\com\shopsphere\eshop\EShopApplication.java`（启动类）
- **问题**：Spring Security 6 需显式 `@EnableMethodSecurity` 才能启用 `@PreAuthorize`。当前 18 处 `@PreAuthorize("hasRole('ADMIN')")`（OrderController、UserController、AdminDashboardController 等）**全部不生效**。
- **修复**：启动类加 `@EnableMethodSecurity`，并在「验证清单」中验证普通用户访问 `/admin/**` 返回 403。
- ✅ 已修复：`EShopApplication` 已加 `@EnableMethodSecurity`；实测普通用户访问管理接口返回 **403**（修复前 500）。

### S2 【高危】管理端接口无角色控制 【✅ 已整改】

- **位置**：`AdminSeckillController`、`AdminCouponController`、`AdminRefundController`、`AdminMerchantApplyController`、`NoticeController`
- **问题**：上述 Controller 连 `@PreAuthorize` 都没有，`SecurityConfig` 中仅 `anyRequest().authenticated()`，任意注册用户可直接调用 `POST /admin/seckill`、`POST /admin/coupon` 等管理操作。
- **修复**：S1 开启后，为所有 `/admin/**`、`/api/admin/**` 补齐 `@PreAuthorize("hasRole('ADMIN')")`，或在 `SecurityConfig` 按路径前缀统一限权。
- ✅ 已修复：全部管理端接口已补齐 `@PreAuthorize("hasRole('ADMIN')")`。

### S3 【高危】优惠券越权使用（不校验归属） 【✅ 已整改】

- **位置**：`OrderServiceImpl.java:138`（`userCouponMapper.selectById(dto.getUserCouponId())`）
- **问题**：只校验了 `status == 0`，未校验 `userCoupon.getUserId().equals(userId)`。攻击者传他人 `userCouponId` 可盗用其优惠券抵扣，并把他人券标记为已使用（236-244 行）。
- **修复**：增加归属校验，不匹配直接抛业务异常。
- ✅ 已修复：已增加 `userCoupon.getUserId().equals(userId)` 归属校验。

### S4 【高危】匿名文件上传 + 无类型白名单 【✅ 已整改】

- **位置**：`SecurityConfig.java:40`（`/api/v1/files/**` permitAll）、`FileUploadController.java:29-62`
- **问题**：未登录即可上传；仅校验非空与 10MB，无扩展名/MIME 白名单。可被用于托管恶意 HTML/JS（存储型 XSS）。
- **修复**：接口改为 `authenticated()`；增加扩展名白名单 + 内容类型（MIME）校验（至少做扩展名校验）。
- ✅ 已修复：上传接口已改为登录后访问，并增加扩展名/类型白名单校验。

### S5 【高危】敏感信息硬编码 【✅ 已整改】

- **位置**：`application.yml:19`（QQ 邮箱 SMTP 授权码）、`application.yml:44`（JWT 签名密钥，注释自带 "please change it"）、`application-dev.yml:8`（MySQL 密码 123456）
- **修复**：改为环境变量注入（`${JWT_SECRET}`、`${MAIL_PASSWORD}`），并从 git 历史清除。
- ✅ 已整改：已支持环境变量注入（开发环境仍保留默认值，正式部署前需移除）。

### S6 【高危】密码重置验证码删除键错误，验证码可无限复用 【✅ 已整改】

- **位置**：`UserController.java:251 vs 266`
- **问题**：写入键为 `"email:code:" + email + ":reset"`，删除时却用 `"email:code:" + email`（少 `:reset` 后缀）→ 验证码永不失效，配合无限次重置密码可被反复利用。
- **修复**：`redisTemplate.delete("email:code:" + request.getEmail() + ":reset")`。
- ✅ 已修复：`UserController.java:266` 已按写入键格式删除。

### S7 【中危】登录日志打印完整 JWT / 验证码可绕过 【🟡 部分已整改】

- **位置**：`UserServiceImpl.java:121`（`log.info("生成的完整 token: {}", token)`）；`UserServiceImpl.login`（验证码仅在同时传了 key+code 时才校验，不传即绕过图形验证码）
- **修复**：JWT 日志改为脱敏（只记 userId/前缀）；验证码改为必填强校验。
- 🟡 已修复：JWT 日志已脱敏（`log.info("用户 {} 登录成功，会话版本: {}", username, sver)`，不再输出完整 token）。
- ⏳ 待整改：验证码绕过（`login` 仍为 `hasText(key) && hasText(code)` 才校验，未改为必填强校验——因涉及前端登录改造，需前后端协同后处理）。

### S8 【中危】已注销用户可被搜索出（OR/AND 优先级错误） 【✅ 已整改】

- **位置**：`UserServiceImpl.searchUsers`（220-227 行）
- **问题**：`like(...).or().like(...).or().like(...)` 后追加 `.eq(deleted, 0)`，生成的 SQL 为 `A LIKE ? OR B LIKE ? OR (C LIKE ? AND deleted=0)`，通过用户名/手机号可搜出已注销用户。
- **修复**：`wrapper.and(w -> w.like(...).or().like(...).or().like(...)).eq(...)` 显式分组。
- ✅ 已修复：已改为 `wrapper.and(w -> ...)` 显式分组（`UserServiceImpl.java:221-227`）。

## 3. 后端并发与事务问题

> **整改状态**：C1-C4 已修复 ✅；C5 待整改 ⏳。

### C1 【高危】下单扣库存非原子（并发超卖） 【✅ 已整改】

- **位置**：`OrderServiceImpl.createOrder`（111-122 行）
- **问题**：`if (sku.getStock() < qty) throw; sku.setStock(stock - qty); updateById(sku)`——先查后扣（check-then-act），并发下两个请求同时读到库存 1 都通过校验 → 超卖。`MybatisPlusConfig` 未注册乐观锁插件；`OrderMapper.selectForUpdate`（FOR UPDATE）定义了却从未使用。
- **修复**（三选一）：
  1. 原子 UPDATE：`UPDATE product_sku SET stock = stock - #{qty} WHERE id = #{id} AND stock >= #{qty}`，返回行数判断成败；
  2. 乐观锁：`@Version` + 失败重试；
  3. Redis 分布式锁兜底。
- ✅ 已修复：采用「条件 UPDATE 原子扣减」（`UPDATE ... SET stock = stock - #{qty} WHERE stock >= #{qty}`，返回行数判成败）。

### C2 【高危】优惠券领取超发 【✅ 已整改】

- **位置**：`UserCouponServiceImpl.receiveCoupon`（128-141 行）
- **问题**：`if (stock <= 0) throw; setStock(stock-1); updateById`，同样 check-then-act，且「检查领取上限」也存在竞态。
- **修复**：条件 UPDATE（`SET stock = stock - 1 WHERE id = ? AND stock > 0`）。
- ✅ 已修复：已改为条件 UPDATE 原子扣减。

### C3 【中危】秒杀 DB 库存丢更新 【✅ 已整改】

- **位置**：`SeckillServiceImpl.seckill`（260-267 行）
- **问题**：Redis 预减做闸门避免了超卖，但 DB 层仍读改写，两个并发请求各读到 N 各写 N-1，DB 库存少扣；一旦 Redis 丢失需 `preheatStock` 恢复时会以错误值预热。
- **修复**：DB 侧同样使用条件 UPDATE。
- ✅ 已修复：DB 侧已改为条件 UPDATE。

### C4 【中危】定时任务自调用导致事务失效 【✅ 已整改】

- **位置**：`OrderServiceImpl.java:51-54`（`@Scheduled` → 内部调用带 `@Transactional` 的 `autoCancelExpiredOrders`）
- **问题**：同 Class 内自调用绕过 Spring AOP 代理，事务不生效，订单取消中途失败会部分回滚。
- **修复**：把 `autoCancelExpiredOrders` 拆到独立 Bean，或直接对外暴露 `@Transactional` 方法由定时入口调用。
- ✅ 已修复：已拆分独立 Bean 调用，定时任务事务生效。

### C5 【低危】类级 `@Transactional` 过宽 【⏳ 待整改】

- **位置**：`NoticeServiceImpl`、`MerchantApplyServiceImpl`（类级注解）
- **修复**：只读方法去掉事务或改 `@Transactional(readOnly = true)`，避免长事务。

## 5. 前端类型与容错问题（高危）

> **整改状态**：F1-F3 已修复 ✅；F4、F5 待整改 ⏳。

### F1 【高危】全屏 loading 遮罩永久泄漏 【✅ 已整改】

- **位置**：`src/utils/request.ts:32-43`（请求拦截器 `showLoading()`）+ `:67-86`（错误拦截器）
- **问题**：
  - 网络错误/超时（无 response）分支（70-73 行）直接 `Promise.reject`，**未调用 `hideLoading()`**；
  - blob/arraybuffer 下载分支（51-53 行）同样未 `hideLoading()`。
  - `requestCount` 只增不减 → 任何一次超时后全局全屏 loading 永久卡死。
- **修复**：错误拦截器入口与 blob 分支补 `hideLoading()`；建议 loading 支持按请求配置开关（轮询/后台请求跳过）。
- ✅ 已修复：错误拦截器与 blob 分支均已补 `hideLoading()`。

### F2 【高危】request 泛型错位：`.get<T>()` 声明与运行时解包结果不一致 【✅ 已整改】

- **修复**：给实例方法重新声明类型 `get<T>(url, config?): Promise<T>`，或统一使用 `request<any, T>({...})` 配置式风格，删除全部 `(res as any).data` 兼容层。
- ✅ 已修复：`request.ts` 已补充实例方法调用签名，TS2349 报错清零，相关页面 hack 已移除。

### F3 【高危】页面绕过 API 层裸调 request 【✅ 已整改】

- **位置**：`seckill/index.vue:149,163`（`request.get("/api/seckill/sessions")`）、`CouponCenter.vue:293,317`

- **修复**：用户端秒杀接口补进 `api/eshop/seckill.ts`；CouponCenter 改用 `user_coupons.ts` 导出函数；删除页内重复类型。
- ✅ 已修复：seckill 页面已改用 `SeckillAPI`，CouponCenter 已改用 `user_coupons.ts` 封装，重复类型已删除。

### F4 【中危】错误提示双重弹出 【⏳ 待整改】

- **位置**：拦截器已 `ElMessage.error`，页面 catch 又弹一次：checkout:322、product/detail:407/418/485、SignIn:234、CouponCenter:250/321
